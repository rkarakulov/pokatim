# Удаление аккаунта

Как устроено — ADR-0015, продукт — `docs/product/account.md`. Удаление синхронно закрывает аккаунт (сессии отозваны,
`users.deletedAt`), данные модулей чистит worker в очереди `account-deletion`; через 15 мин — повторный проход, раз в
час регламент `account.erasure-resume` перезапускает незавершённые. Логи — только `user=<uid>`, без e-mail.

Шаги стирания по порядку: профиль (жалобы на пользователя `profile_reports` по `targetUserId`, анкета Verified, фото
`profile_avatars` по `userId`, затем документ `profiles`) → райды → «Мои маршруты» → устройства → заезды → … → `tickets` (активные регистрации на старты календаря и билеты →
`cancelled`, место освобождается; документы остаются псевдонимными; лог `registrations=<n> tickets=<n>`, ADR-0023) →
`notifications` (уведомления,
настройки, push-токены, квитанции Expo; лог `deleted=<n> settings=<0|1> tokens=<n>`, ADR-0017) → identity. Push-токены
снимаются ещё раньше — в транзакции удаления: push удалённому не уходят с момента подтверждения.

## 1. Ручной шаг Open Wearables (A8)

Ключ API не удаляет пользователя агрегатора — после очистки в OW остаётся пустой пользователь
`external_user_id = pokatim:<userId>` без подключений.

1. Найти удалённых за период (mongosh, база API):
   `db.users.find({ deletedAt: { $gte: ISODate('<с>') } }, { _id: 1, deletedAt: 1 })`.
2. В админке OW найти пользователя по `external_user_id = pokatim:<_id>` и удалить его.
3. Проверка: в OW такого пользователя нет; в pokatim `device_accounts` с `_id` пользователя нет.

## 2. Отзыв подключения не удался (`revokeFailed`, `DEVICES_ENABLED=false`)

Признак — `device_audit` с `action: 'revoke_failed'`, `reason: 'account_deleted'` (сами подключения уже удалены) или
лог `devices.revoke_failed connection=<id>`. Отозвать доступ провайдера вручную в OW (подключение пользователя
`pokatim:<userId>`) или попросить владельца отозвать доступ «Покатим» в Garmin Connect / Wahoo.

## 3. Зависшая очистка

Признак: удалён больше 2 ч назад, повторный проход не завершён.

```js
db.users.find(
  { deletedAt: { $type: 'date', $lt: new Date(Date.now() - 2 * 3600e3) }, erasureSweptAt: { $eq: null } },
  { _id: 1, deletedAt: 1, erasedAt: 1, deletionEmailSentAt: 1 },
)
```

- Лог worker `account.erasure_failed user=<uid> step=<шаг>` — какой шаг падает (финальная попытка задачи).
- Задача в failed-наборе BullMQ (`removeOnFail: false`): очередь `account-deletion`, имя
  `account.deletion-requested` или `account.deletion-sweep`.
- Повтор: дождаться регламента (раз в час, `account.erasure-resume`) или вручную `retry` failed-задачи (Bull Board /
  `queue.getJob(id).retry()`). Все шаги идемпотентны — повтор безопасен.
- Шаг `identity` не проходит из-за почты: через 24 ч после удаления e-mail стирается без письма (лог
  `account.deletion_email_abandoned`).
- Регламент берёт за запуск не больше 50 аккаунтов (`resumeBatch`), самые давние первыми. Если больше 50 застряли и
  падают снова, более поздние ждут без повтора («голодание»). Признак — запрос выше возвращает больше 50 строк.
  Действия: устранить причину сбоя шага (лог `account.erasure_failed`) и вручную `retry` failed-задачи; ротации
  выборки нет (нужно новое поле в `users`) — сделать, если ситуация повторится.

## 4. Второе письмо «Аккаунт удалён» (R6)

Если worker упал между отправкой письма и отметкой `deletionEmailSentAt`, после истечения захвата (5 мин) письмо уйдёт
повторно. Это принятый риск (at-least-once), действий не требуется.

## 4a. Адрес поддержки в письме (`SUPPORT_EMAIL`)

Строка «Если это были не вы — напишите на …» есть в письме, только если задан `SUPPORT_EMAIL` (письма уходят с
no-reply). На dev переменная пустая. **До прода задать** в `.env` сервера, затем перезапустить worker.

## 5. Ротация `EMAIL_TOKEN_SECRET` (R8)

Маркер стёртого e-mail — HMAC этим ключом. После ротации адреса удалённых аккаунтов снова можно зарегистрировать
(блок D-07 снимается), ссылки из уже отправленных писем перестают работать. Ротировать — только осознанно, с записью
в журнал изменений. Ротация инвалидирует и QR билетов на мероприятия — runbook «Деплой», раздел «Билеты».

## 6. Юридический риск (D10, R1)

Журналы согласий (`user_consents`, `profile_consent_events`) и аудит хранятся после удаления с псевдонимным `userId`.
Правомерность — проверить юристом до прода.
