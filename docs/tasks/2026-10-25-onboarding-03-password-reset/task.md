# 1. Title

Онбординг, слайс 3: сброс пароля по ссылке из письма, отзыв всех сессий, уведомление о смене пароля

# 2. Goal

Райдер «Покатим» (`docs/product/brand.md`), забывший пароль, на любой платформе (iOS, Android, web/PWA) запрашивает
ссылку по e-mail, открывает её из письма, задаёт новый пароль и входит с ним. Смена пароля отзывает **все** сессии
аккаунта на всех устройствах (`revoked_reason = 'password_reset'`) и сообщает владельцу письмом. Ссылка одноразовая, с
TTL, открытие ничего не меняет, смена — POST по кнопке (`security.md`, `onbike-security.md`).

Закрываются хвосты:

- слайс 1, Out of Scope: «Сброс пароля — слайс 3»;
- слайс 2, Out of Scope и §12: «Сброс пароля и ссылка „Забыли пароль?“ — слайс 3 … инвалидация всех сессий пользователя
  при сбросе (отзыв по `user_id`)»; ADR-0005 «Пересмотреть: со сбросом пароля (отзыв всех сессий по `user_id`)», Q8
  слайса 2 («выйти везде» — со сбросом пароля).

Источники значений: правила безопасности проекта; образцы — подтверждение e-mail (ADR-0002: токен ссылки = HMAC от id
строки, outbox → BullMQ → письмо, захват отправки) и вход (ADR-0005: лимиты `RateLimiter`, нейтральные ответы).
Описания экранов сброса и их текстов в `docs/product/` нет (`prototypes.md` отсутствует) — раскладка и тексты помечены
`[ASSUMPTION]` и вынесены автору (§8.1, «Вопросы автору»).

# 3. Scope

**Contracts / api-client** (`packages/contracts/src/auth/password-reset.schema.ts` — новый; `packages/api-client`)
- `RequestPasswordResetRequest { email }` → `RequestPasswordResetResponse { resendAvailableInSec }` — один и тот же
  ответ для любого адреса.
- `PasswordResetLinkInfo` (union по `state`: `valid` | `expired` | `used`, все с `email`) — чтение ссылки без побочных
  эффектов.
- `ConfirmPasswordResetRequest { token, password }` (пароль — `Password` регистрации, 8–128) →
  `ConfirmPasswordResetResponse { state: 'passwordChanged', email }`.
- Новых кодов ошибок нет: `LINK_EXPIRED` (410, `LinkExpiredDetails { email }`), `NOT_FOUND`, `RATE_LIMITED`,
  `VALIDATION_FAILED` — существующие. Клиент: `requestPasswordReset`, `getPasswordResetLink`, `confirmPasswordReset`.

**API — модуль `identity`**
- `POST /v1/auth/password-reset` — запрос ссылки по e-mail. Лимиты до обращения к БД (`RateLimiter` базы, ключи —
  HMAC): IP, затем e-mail (пауза + суточный предел), по очереди до первого отказа; `429 RATE_LIMITED` + `retryAfterSec`
  одинаково для существующих и несуществующих адресов. Ответ `200 { resendAvailableInSec }` — один для всех адресов;
  письмо уходит только существующему не удалённому аккаунту (неподтверждённому — по Q4). Новая ссылка отменяет прежние
  (Q6). В транзакции — строка ссылки + outbox-событие; письмо отправляет worker.
- `GET /v1/auth/password-reset/:token` — только чтение: `valid` | `expired` (истекла или заменена) | `used`; неизвестный
  токен, мусор, удалённый аккаунт — `404 NOT_FOUND`.
- `POST /v1/auth/password-reset/confirm` — одна транзакция под `lockUser`: новый хеш пароля (argon2id, посчитан до
  транзакции), ссылка `used`, **все** живые сессии пользователя отозваны (`revoked_reason = 'password_reset'`), токен
  регистрации погашен, неподтверждённый e-mail подтверждён (Q4), outbox-событие письма «Пароль изменён». Ответ —
  `passwordChanged` + e-mail; сессии не выдаёт (Q2). Устаревшая/заменённая/использованная ссылка — `410 LINK_EXPIRED`
  с e-mail; argon2 — только после проверки токена.
- Вход: под `lockUser` повторно сверяется хеш пароля — вход, проверивший **старый** пароль до коммита сброса, сессию
  не получает (§8.1 R4).
- Worker: письмо со ссылкой сброса (захват отправки как у подтверждения) и письмо «Пароль изменён» (без ссылки с
  токеном) — очередь `identity-email`, один процессор с разбором по имени задачи (§8.1 R6).
- Миграция `0005_password_reset` (expand-only): таблица `password_reset_tokens`; CHECK `sessions.revoked_reason` +
  `'password_reset'`.

**App (`apps/app`, все платформы)**
- «Вход»: `TextAction` «Забыли пароль?» → экран `/forgot-password` (группа `(onboarding)`): e-mail (подставлен из формы
  входа через черновик в памяти, не через URL), «Отправить ссылку» → состояние «Проверьте почту» с нейтральным текстом,
  повтором с отсчётом (`resendAvailableInSec` / 429 `retryAfterSec`) и «Вернуться ко входу». SSR + `generateMetadata`,
  `DocumentTitle`.
- Ссылка из письма — `src/app/auth/reset/[token].tsx` (вне гардов, как `auth/verify/[token]`): GET-состояние →
  `valid`: форма «Новый пароль» (+ «Повторите пароль» — Q8, `autoComplete="new-password"`), «Сохранить пароль» (POST);
  `expired`: «Ссылка устарела» + «Отправить новую ссылку» (запрос по e-mail из ответа GET) + «Вернуться ко входу»;
  `used`: «Пароль уже изменён» + «Войти»; 404: «Ссылка больше не действует» + «Вернуться ко входу». SSR без токена и
  e-mail в HTML (без `loader`, без `og:url`).
- Успех: «Пароль изменён. Войдите с новым паролем» → «Войти» → `/sign-in` с e-mail в черновике (Q2). Была сессия на
  этом устройстве — локальный выход (`useSignOut`: сервер, хранилище, `queryClient.clear()`), она всё равно отозвана.
- Web: ответ 410 на сохранение перечитывает состояние ссылки (`used`/`expired`); мутации — `networkMode: 'always'`.
- Web-сервер: `Referrer-Policy: no-referrer` для путей `/auth/*` (ссылки с токеном — §8.1 R9).

**E2E / docs** — шаги смоука `e2e/web.spec.ts` (SSR `/forgot-password`, `/auth/reset/<токен>`; с API: запрос → письмо
в Mailpit → новый пароль → старый пароль 401 → вход новым → письмо «Пароль изменён»); ADR-0006, правки ADR-0002/0005,
architecture, rules, runbook (§10).

# 4. Out of Scope

- Смена пароля из профиля (по старому паролю), экран «Устройства» / «Выйти на всех устройствах» отдельно от сброса.
- Проверка пароля по утечкам (HIBP и т. п. — внешний сервис, AGENTS.md §4.9), история паролей / запрет повтора
  старого, политика сложности сверх 8–128.
- Отзыв выданных access JWT до истечения (≤ 15 мин): авторизованных эндпоинтов нет; решение — с первым AuthGuard
  (проверка `sid` по `sessions.revoked_at` или принятые 15 мин) (§8 «Access после сброса»).
- Мгновенный выход других вкладок/устройств (BroadcastChannel, `AppState`, push) — Q9; в слайсе 3 они узнают об
  отзыве при следующем refresh/старте.
- Universal / app links (https-ссылка открывает приложение) — слайс 5; ссылка в письме — `APP_LINK_BASE` окружения,
  как у подтверждения.
- Письмо «аккаунта с таким адресом нет» на неизвестный адрес (Q11 — не шлём).
- Журнал аутентификации append-only (`auth_events`) — Q10 (как Q9 слайса 2).
- Очистка истёкших/использованных строк `password_reset_tokens` (как и `sessions`) — задача обслуживания.
- Снятие блокировки входа после сброса (лимитер без `reset` — R2 слайса 2): после сброса вход может ещё ждать ≤ 15 мин
  — §8.
- Переключатель видимости пароля в `TextField` — задача в базу (follow-up), не в проекте.
- Изменения app-foundation.

# 7. Implementation Notes

- **Токен ссылки сброса** (как B1/ADR-0002): `base64url(HMAC-SHA256(EMAIL_TOKEN_SECRET, "password-reset:" + id))`, в БД —
  sha256; worker пересобирает ссылку `${APP_LINK_BASE}auth/reset/<token>` по id из outbox. Префикс отличается от
  `email-verify:` — токен одной ссылки не годится в другую (и таблицы разные). Новый секрет не нужен.
- **Запрос (`requestReset`):** контракт → `normalizeEmail` → `consume` IP → `consume` e-mail (по очереди до первого
  отказа, как `SignInService.takeAttempt`; 429 — пауза отказавшего правила) → `findUserByEmail` → нет/удалён (или
  неподтверждён при Q4 ≠ «а») — ответ тот же, без записи → иначе транзакция: `lockUser` (перепроверка «не удалён») →
  `supersedeActivePasswordResetTokens` → `nextId` + insert (`expires_at = now + TTL`) → `outbox.append(...)` → ответ
  `{ resendAvailableInSec: cooldownSec }`. Лимит e-mail считается и для несуществующих адресов — 429 не выдаёт аккаунт.
  Остаточная разница времени ответа (вставка + outbox, единицы мс) принята: регистрация и так раскрывает занятость
  адреса (`EMAIL_TAKEN`, слайс 1, принято прототипом).
- **Чтение ссылки:** `findPasswordResetByHash` → нет / пользователь удалён → 404; `used_at` → `used`; заменена или
  истекла → `expired`; иначе `valid`. E-mail во всех состояниях (владелец ссылки — владелец ящика; нужен для повторного
  запроса и подстановки во «Вход»).
- **Смена пароля (`confirmReset`):** `findPasswordResetByHash` (пул) → 404 / 410 до argon2 → `hasher.hash(password)` →
  транзакция: `lockUser` → перечитать ссылку под замком (её могли использовать/заменить параллельно) → 404 / 410 →
  `updatePasswordHash` → `markPasswordResetUsed` → `revokeAllSessions(userId, now, 'password_reset')` (одним UPDATE по
  `sessions_user_id_idx`, `WHERE revoked_at IS NULL`) → `expireRegistrationToken(userId, now)` (`expires_at =
  LEAST(expires_at, now)` — висящий токен регистрации больше не обменяется на сессию, R5) → неподтверждён и Q4 = «а» —
  `markEmailVerified` → `outbox.append(PASSWORD_CHANGED…)` → ответ. Лог: `{ msg: 'password reset', uid, revoked: n }` —
  без e-mail, токенов, IP.
- **Гонки** (все мутации аккаунта — под `lockUser`): два confirm одной ссылкой → второй 410; confirm и вход: вход
  проверяет пароль до транзакции, поэтому под `lockUser` сверяет, что `password_hash` не изменился с момента проверки,
  иначе 401 `INVALID_CREDENTIALS` (R4); confirm и ротация refresh — построчная блокировка `sessions`: ротация после
  отзыва — 0 строк → 401, отзыв после ротации перепроверяет `revoked_at IS NULL` на новой версии строки и отзывает;
  confirm и poll регистрации — poll под `lockUser` видит погашенный токен → 401; confirm и запрос новой ссылки — запрос
  заменяет только активные (использованная не трогается).
- **Письма:** `mail/password-reset-email.ts` (тема «Восстановление пароля», кнопка «Задать новый пароль», «Ссылка
  действует 1 час. Если вы не запрашивали сброс, проигнорируйте письмо — пароль не изменится.») и
  `mail/password-changed-email.ts` («Пароль изменён» {дата и время по Минску}; «Если это были не вы, восстановите
  пароль через „Забыли пароль?“ на экране входа» — без ссылки с токеном). HTML с экранированием, как
  `verification-email.ts`; «Покатим» — по `brand.md`. Тексты — Q7.
- **Процессор `identity-email`:** один `@Processor(QUEUE.identityEmail)`, `process` разбирает `job.name` (три события,
  неизвестное — ошибка, как сейчас) и делегирует обработчикам: подтверждение (как есть), ссылка сброса (захват
  `send_claimed_at`/`sent_at`; пропуск, если ссылка заменена/использована/истекла или аккаунт удалён), «Пароль изменён»
  (at-least-once без захвата: дубль уведомления безвреден; пропуск, если аккаунт удалён).
- **App:** `requestPasswordReset`/`confirmPasswordReset` — мутации с `AUTH_MUTATION`; **без** `withSessionLock`: эти
  запросы cookie сессии не видят и не меняют (путь вне `SESSION_COOKIE.path`). Локальный выход после успеха — через
  `useSignOut` (на web — под Web Lock, со своим `signOutPending`). E-mail во «Вход» — `registration-store.saveDraft`.
  Схема формы — `ConfirmPasswordResetRequest.pick({ password })` + поле повтора с `refine` на клиенте (Q8; сервер
  получает один пароль).
- **Тексты** — `packages/i18n/src/ru.ts`, формальное «вы»; финальные — по ответу автора (Q7).

# 8. Risks / Assumptions / Open Questions

- **Access после сброса (принято).** Отзыв гасит refresh; выданный access JWT живёт ≤ 15 мин. Авторизованных эндпоинтов
  нет — данных за ним нет. С первым AuthGuard — решить (проверка `sid` или принятые 15 мин) — follow-up.
- **Другие вкладки и устройства (Q9).** Вкладка того же браузера, где был вход, держит access в памяти до перезагрузки
  (затем refresh → 401 → «Вход»); native другого устройства — до следующего холодного старта (фоновая ротация → 401).
  Без авторизованных эндпоинтов утечки нет.
- **Блокировка входа после сброса.** Лимитер не умеет `reset` (R2 слайса 2): если перед сбросом исчерпаны попытки
  входа, «Вход» покажет отсчёт до конца окна (≤ 15 мин). Редко; follow-up — примитив лимитера в базе.
- **Задержка писем.** Только последняя ссылка (Q6): пользователь, запросивший дважды и открывший первое письмо, увидит
  «Ссылка устарела» с повтором. Пауза 60 с снижает частоту.
- **Исчерпание суточного лимита чужим (ревью pass 1, LOW, принято).** Лимит e-mail (5 писем в сутки) общий для всех
  IP: посторонний, знающий адрес, может выбрать его, и владелец до суток не получит письмо сброса (429 с отсчётом).
  IP-лимит (20 в час) ограничивает один источник, но не распределённый. Follow-up — ключ e-mail+подсеть (как пара
  e-mail+IP у входа) или поднятый потолок e-mail при отдельном лимите пары.
- **Отправка — at-least-once** (как подтверждение): SMTP принял, worker упал до `sent_at` → по истечении захвата дубль с
  той же ссылкой. Финальный провал задачи (5 попыток) пользователю не виден — он повторяет запрос (как у подтверждения).
- **Токен в URL.** Ссылка `/auth/reset/<токен>` остаётся в истории браузера (после смены — мёртвая); `Referer` —
  `no-referrer` для `/auth/*` (R9); Caddy без access-лога; токен в пути `GET /v1/auth/password-reset/:token` —
  как у подтверждения (логи API пути не пишут).
- `[ASSUMPTION]` Раскладка экранов — по образцу «Подтвердите e-mail» / экрана ссылки подтверждения (`AuthScreen`,
  кикер «Вход», заголовок, текст, поля, кнопка, текстовые действия); прототипа в репозитории нет.
- `[ASSUMPTION]` Старые сборки native без маршрута `auth/reset` — только у внутренних тестеров.

# 8.1 Requirements Consistency

Architecture Review — onboarding-03-password-reset. **Status: CONCERNS** — блокеров нет; продуктовые вопросы Q1–Q11 —
автору (human gate), без ответа реализуется рекомендация. Решения R1–R9 — архитектора, оркестратор может переиграть.

- **R1. «Ссылка web / app-link на native» — недоопределено в постановке.** Ссылка в письме одна:
  `${APP_LINK_BASE}auth/reset/<токен>` (база — конфиг окружения, ADR-0003 п. 5): dev Expo Go — `exp://…/--/`, сборки —
  `onbike://`, web/e2e — `http(s)://<хост>/`. Выбор по платформе запроса — нет (письмо открывают на другом устройстве);
  https-ссылка, открывающая приложение, — universal/app links слайса 5. Альтернативы: (а) **как подтверждение** — одна
  база окружения; (б) две ссылки в письме («в приложении» / «в браузере») — путает, и до домена universal links всё
  равно нет. **Рекомендую (а).**
- **R2. Нейтральный запрос без оракула.** Ответ одинаков для существующего, несуществующего, удалённого (и, при Q4 ≠
  «а», неподтверждённого) адреса; 429 по e-mail — по HMAC адреса до поиска в БД, поэтому тоже одинаков. Альтернатива —
  тихо глотать запросы сверх паузы (всегда 200): нет оракула, но интерфейс говорит «отправили», когда письма нет. Нет.
- **R3. Сброс не выдаёт сессию; путь вне `/v1/auth/session` (Q2).** Альтернативы: (а) **«Пароль изменён» → «Войти» с
  подставленным e-mail** — OWASP Forgot Password: не входить автоматически; менеджер паролей сохраняет новый пароль на
  форме входа; эндпоинт не трогает cookie и Web Lock; (б) сессия в ответе confirm по `sessionTransport` — на шаг короче,
  но путь должен быть под `SESSION_COOKIE.path` (отзыв прежней cookie, `superseded`), запрос — под Web Lock, а сессия
  появится там, где открыли письмо (часто не то устройство); (в) сессия только если ссылку открыли там, где запрашивали
  (нужен токен запроса, как ADR-0002) — сложность без пользы. **Рекомендую (а).**
- **R4. Гонка «вход старым паролем ↔ сброс» — дефект при наивной реализации.** `SignInService` проверяет пароль до
  транзакции, `lockUser` берёт после: вход, проверивший старый пароль, дождётся коммита сброса и получит **новую**
  сессию после «выйти везде». Решение: под `lockUser` перечитать `password_hash` и сравнить с проверенным; иначе 401.
  Альтернатива — проверять пароль под замком (argon2 ~50 мс держит строку `users`; хуже под нагрузкой). Тест на двух
  соединениях обязателен.
- **R5. Неподтверждённый аккаунт + висящий токен регистрации — дыра при Q4 = «а».** Сценарий: злоумышленник
  регистрирует чужой адрес (`EMAIL_TAKEN` для владельца до 7 дней) и держит токен регистрации; владелец сбрасывает
  пароль → e-mail подтверждён → poll злоумышленника обменивает токен на **сессию** в аккаунт владельца. Решение:
  confirm гасит токен регистрации в той же транзакции (`expires_at = now`; poll → 401) — всегда, независимо от Q4.
  Остаточное: дата рождения и согласия аккаунта введены регистрантом (не владельцем) — продуктовый/юридический
  нюанс, вынесен в Q4.
- **R6. Очередь писем: один процессор на `identity-email`.** `VerificationEmailProcessor` — единственный
  `@Processor(QUEUE.identityEmail)` и бросает на чужие имена задач; второй процессор на той же очереди получал бы чужие
  задачи (BullMQ раздаёт по очереди, не по имени). Альтернативы: (а) **один процессор-диспетчер по `job.name` +
  обработчики** (комментарий `queues.ts`: «позже — сброс пароля»; SMTP-конкурентность — в одном месте); (б) отдельная
  очередь `identity-password-email` со своим процессором — без рефакторинга, но ещё одна очередь на тот же SMTP.
  **Рекомендую (а)**; int-тесты подтверждения сохраняются (вызов обработчика по id события).
- **R7. Аудит (Security §6).** Сброс пароля — чувствительное действие; append-only журнала входов нет (Q9 слайса 2).
  Альтернативы: (а) **строка ссылки (`created_at`, `used_at`) + `sessions.revoked_reason = 'password_reset'` +
  структурный лог `{ uid, revoked }`** — без новой подсистемы; (б) журнал `auth_events` (запрос, смена, отзыв) —
  отдельная задача с решением о хранении ПДн. **Рекомендую (а)** (Q10). Строки ссылок не удаляются кодом (только каскад
  при удалении аккаунта и будущая очистка).
- **R8. Новых кодов ошибок не вводим.** «Ссылка устарела / заменена / использована» на POST — `410 LINK_EXPIRED` с
  `LinkExpiredDetails { email }` (как подтверждение); точное состояние клиент получает повторным GET (`used` →
  «Пароль уже изменён. Войдите»). Повтор POST после потерянного ответа → 410 → GET `used` → «Войти» — пароль уже новый,
  исход верный. Альтернатива — идемпотентный 200 на использованную ссылку (как confirm подтверждения): соврёт, если
  повтор пришёл с другим паролем. Нет.
- **R9. `Referrer-Policy: no-referrer` для `/auth/*`** (web-сервер приложения). Сейчас `strict-origin-when-cross-origin`:
  наружу уходит только origin, но same-origin запросы к API (прод — один origin за Caddy) несут полный `Referer` с
  токеном. Дёшево и закрывает и ссылку подтверждения. Альтернатива — `<meta name="referrer">` в `+html.tsx` для всех
  страниц (шире, затрагивает шаблонный файл). **Рекомендую заголовок по префиксу пути.**
- **Конфликтов с инвариантами AGENTS.md §4 нет:** контракт первым (§4.2), письма — outbox + worker (§4.5), миграция
  expand-only отдельным шагом (§4.6), UI из системы без новых компонентов (§4.11), скелетон на месте данных ссылки
  (§4.12), все платформы, экран по ссылке — SSR без ПДн (§4.13), внешних сервисов нет (§4.9).
- **Недоопределено (продукт) — Q1–Q11 ниже.** Не блокируют: у каждого — рекомендация по умолчанию.

# 8.3 Security checklist

Затронуты аутентификация и сессии, публичные ссылки из писем, персональные данные (e-mail) — `security.md`,
`onbike-security.md`.

1. **AuthN/AuthZ.** Все три эндпоинта публичные. Смена пароля — только по живой (не использованной, не заменённой, не
   истёкшей) ссылке не удалённого аккаунта; проверка — на сервере, под `lockUser` с перепроверкой ссылки (гонки).
   Сессий сброс не выдаёт (Q2); отзывает **все** сессии пользователя (`password_reset`) и гасит токен регистрации (R5).
   Вход после сброса — только новым паролем, включая гонку с уже проверенным старым (R4). CSRF — глобальный
   `enableCsrfProtection` (Fetch Metadata + Origin) для POST; cookie сессии эти пути не получают.
2. **Входные данные.** Zod-контракты, `z.strictObject` (лишние ключи — 400): `Email` (≤ 254, trim), `Password` 8–128
   (верхний предел ограничивает работу argon2), токен — `OpaqueToken` (43 символа base64url); токен в пути GET не по
   формату — 404 до БД (как подтверждение).
3. **Данные наружу.** Запрос — один и тот же ответ `{ resendAvailableInSec }` для любого адреса; e-mail отдаётся только
   владельцу ссылки (GET, 410, ответ confirm). Ответы без id пользователя, хешей, сроков сессий. SSR экранов: без
   `loader`, без e-mail и токена в HTML/мета, без `og:url` у пути с токеном; `Cache-Control: no-store` у ответов API;
   `Referrer-Policy: no-referrer` для `/auth/*` (R9).
4. **Злоупотребления.** Лимиты запроса (Q5): IP → e-mail по очереди до первого отказа, 429 + `retryAfterSec` одинаково
   для несуществующих адресов; письмо — только существующему аккаунту, неизвестному — нет (Q11); argon2 в confirm —
   только после проверки токена; токен — 256 бит HMAC, перебор невозможен; одна активная ссылка (Q6), TTL 1 ч (Q1).
5. **Секреты и логи.** Сырой токен — только в письме: в БД sha256, в outbox/BullMQ — id строки, ссылка пересобирается
   HMAC в worker; в Redis — HMAC-ключи, не e-mail/IP; новый пароль — только argon2id; логи — `uid`, число отозванных
   сессий, id события; e-mail, токены, пароли, IP не логируются (тест на вызовы логгера); клиент: `console.warn` —
   только имя ошибки.
6. **Аудит.** `password_reset_tokens.created_at/used_at`, `sessions.revoked_reason = 'password_reset'` + `revoked_at`,
   структурный лог; журнала `auth_events` нет (R7, Q10). Append-only таблиц не меняем.

# 9. Acceptance Criteria

1. Запрос: существующий подтверждённый адрес (любой регистр, пробелы по краям) → 200 `{ resendAvailableInSec: 60 }`,
   строка ссылки, событие outbox, письмо в Mailpit со ссылкой `${APP_LINK_BASE}auth/reset/<43 символа>`; sha256 ссылки
   = `token_hash`. Неизвестный и удалённый адрес → тот же 200 побайтно, ни строки, ни письма.
2. Лимиты (Q5): второй запрос раньше 60 с и 6-й за сутки → 429 `RATE_LIMITED` + `retryAfterSec`, одинаково для
   несуществующего адреса; лимит IP; отказ по IP не создаёт счётчика e-mail.
3. Новая ссылка отменяет прежнюю (Q6): старая → GET `expired`, POST 410. Письмо заменённой/истёкшей ссылки не уходит.
4. GET ничего не меняет (строки, сессии, хеш пароля — как были): `valid` / `expired` (истекла — фиксированный CLOCK +1 ч)
   / `used`; мусор, неизвестный токен, удалённый аккаунт → 404.
5. Confirm: пароль заменён (вход старым → 401, новым → 200); ссылка `used`; **все** живые сессии пользователя
   отозваны (`password_reset`), чужие сессии и уже отозванные — без изменений; refresh любой из них → 401; повтор
   confirm → 410; пароль короче 8 / длиннее 128 / лишний ключ → 400 до argon2; письмо «Пароль изменён» в Mailpit без
   токена.
6. Неподтверждённый (Q4 = «а»): письмо сброса уходит; после confirm `email_verified_at` выставлен, poll прежним
   токеном регистрации → 401, вход новым паролем → `signedIn`.
7. Гонки (два соединения): вход, проверивший старый пароль до коммита сброса, → 401 и без новой строки `sessions`;
   два confirm одной ссылкой → один 200, один 410.
8. App (iOS, Android, web): «Забыли пароль?» на «Входе» → `/forgot-password` с e-mail из формы входа → «Проверьте почту»
   с отсчётом и повтором (429 — отсчёт); ссылка → «Новый пароль» (скелетон на месте данных до ответа GET; ошибки полей;
   кнопка `loading`; «Пароли не совпадают») → «Пароль изменён» → «Вход» с e-mail; состояния `expired` (новая ссылка),
   `used`, 404, сеть/офлайн — баннеры с повтором; сессия на этом устройстве после сброса — локальный выход.
9. Web SSR: `/forgot-password` и `/auth/reset/<токен>` — HTML формы/скелетона, `<title>`/OG без ПДн, без токена в мета
   и без `og:url` у пути с токеном; `Referrer-Policy: no-referrer` на `/auth/*`. Смоук с API: вход → выход → «Забыли
   пароль?» → письмо → новый пароль → старый 401 → вход новым → письмо «Пароль изменён».
10. Архитектура: контракты — первыми; захват отправки — одна реализация; один процессор `identity-email`; сессии не
    выдаются сбросом; DTO только из contracts; без `Platform.OS` в экранах; миграция на чистой БД; `pnpm check` зелёный;
    int-тесты на реальных PostgreSQL + Redis.
