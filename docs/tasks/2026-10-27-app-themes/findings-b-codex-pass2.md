### [MEDIUM] Web может применить тему до завершения загрузки её шрифтов

- **file:** apps/app/src/theme/use-theme-fonts.ts
- **location:** `allLoaded`, строки 14–15; `useClientThemeFonts`, строка 47
- **problem:** Пока `Font.loadAsync` ещё выполняется, повторный рендер проверяет `Font.isLoaded` и может вернуть `ready: true`. На web `expo-font` добавляет `@font-face` до ожидания `document.fonts.load`, а `isLoaded` считает наличие этого CSS-правила признаком готовности.
- **why_it_matters:** `AppThemeProvider` переключит тему до скачивания шрифтов: текст сначала появится системным шрифтом, затем сменит гарнитуру. Это нарушает AC4. В B все темы используют одинаковые шрифты, но механизм доставки разных наборов уже входит в этот слайс.
- **evidence:** В установленном `node_modules/expo-font/build/ExpoFontLoader.web.js` создание CSS-правила предшествует ожиданию `document.fonts.load`; `isLoaded` проверяет наличие правила. Фактический хук воспроизведён в памяти с таким поведением загрузчика: после эффекта `{ ready: false }`, после повторного рендера `{ ready: true }`, хотя Promise скачивания остаётся незавершённой.
- **recommended_fix:** Не считать набор готовым, пока его загрузка выполняется: учитывать `Font.isLoading` или хранить состояние незавершённых загрузок. Сохранить готовность SSR-шрифтов при гидрации. Добавить тест: CSS уже зарегистрирован, загрузка не завершена, повторный рендер — прежняя тема сохраняется.

### [MEDIUM] Два окна кэширования могут задержать обновление SSR-темы почти на 120 секунд

- **file:** apps/app/src/features/appearance/ssr-theme.ts
- **location:** `refreshSsrTheme`, строки 53–57
- **problem:** Окно попыток начинается перед запросом, а TTL кэша `fetchPublicForSsr` — после получения ответа. Через 60 секунд новая попытка может прочитать ещё действующий старый кэш и одновременно отложить следующее обновление ещё на 60 секунд.
- **why_it_matters:** Даже при постоянном трафике и исправном API сервер продолжает отдавать прежнюю тему существенно дольше заявленных примерно 60 секунд (T2, R2, ADR-0016).
- **evidence:** Воспроизведено в памяти на фактических `ssr-theme.ts` и `public-ssr.ts`: первый ответ получен на отметке 500 мс; API затем переключён на `journal`. Обращение на 60 000 мс вернуло кэшированный `atlas`, на 61 000 мс запрос заблокирован новым окном; второй реальный fetch произошёл только на 120 000 мс. Текущие тесты мокают `fetchPublicForSsr`, поэтому взаимодействие двух окон не проверяют.
- **recommended_fix:** Согласовать окно обновления с завершением попытки и TTL существующего кэша, сохранив single-flight и ограничение повторов после ошибок. Добавить тест с настоящим `fetchPublicForSsr`, задержанным ответом и управляемым временем.

Предыдущие находки про single-flight, повторные запросы при сбое и возврат к загруженному набору шрифтов закрыты. CRITICAL/HIGH не обнаружены.
