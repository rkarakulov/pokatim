### [HIGH] Финишёры теряются за общим пределом таблицы
- **file:** apps/admin/src/features/results/StandingsTable.tsx
- **location:** 245, 278–286, 301–312
- **problem:** Блок финишёров формируется из уже ограниченного ответа «Участников». При 1000 ранжированных строках и одной START-заявке со временем сервер вернёт только ранжированные строки. KPI покажет одного финишёра, а его таблица — «Нет финишёров по выбранным фильтрам».
- **why_it_matters:** Команда не сможет посмотреть результат START. Выбрать его группу отдельно тоже нельзя: варианты фильтра берутся из групп с местами, куда START с `groupKey: overall` не входит. Требование 07b об отдельной таблице финишёров фактически не выполняется для большой гонки.
- **evidence:** `ResultsPanelReadService.standingItems` сначала добавляет `headRows.slice(0, max)`, затем остальные заявки только в оставшиеся места; `RESULTS_POLICY.standingsMax = 1000`. Здесь `finishers = items?.filter(...)` применяется после ограничения. `groups` сервер формирует по ранжированным строкам. Предупреждение об усечении находится только в секции «Участники».
- **recommended_fix:** Загружать финишёров независимо от лимита ранжированных участников: добавить серверный фильтр финишёров и отдельный запрос с пагинацией либо отдельный панельный endpoint. Не показывать пустое состояние как отсутствие финишёров при усечённом ответе. Добавить тест «1000 участников с местами + START-финишёр».

### [HIGH] Ошибка обновления анкеты скрывается без возможности повтора
- **file:** apps/admin/src/features/results/VerifiedDemographicsDialog.tsx
- **location:** 174–195
- **problem:** При наличии `current.data` компонент сразу возвращает форму, игнорируя `current.isError`. После неудачного фонового обновления текущих значений нет ни сообщения об ошибке, ни кнопки повтора.
- **why_it_matters:** Нарушен AGENTS.md §4.12: ошибка обновления при показанных данных должна оставлять данные и показывать баннер с повтором. Администратор продолжает редактирование, не зная, что актуальность исходных значений проверить не удалось.
- **evidence:** Ветка `if (current.data)` предшествует проверке ошибки. `verifiedDemographicsQuery` задаёт `staleTime: 0`; глобальный QueryClient не отключает обновление при восстановлении соединения. Следовательно, после успешной загрузки возможен повторный GET с ошибкой и сохранёнными данными.
- **recommended_fix:** В ветке с данными сохранять форму и отображать баннер ошибки обновления с вызовом `current.refetch()`. Добавить тест: успешная загрузка → ошибка повторного GET → форма остаётся, баннер и повтор доступны.

### [MEDIUM] Метрика развязки половин заезда подписана как доля рывков
- **file:** packages/i18n/src/ru.ts
- **location:** 1814, `admin.results.flagMetric.HR_POWER_DECOUPLED`
- **problem:** Для любого `HR_POWER_DECOUPLED` выводится «{value} % рывков без ответа пульса», хотя метрика этого флага может означать процент расхождения Pw:HR между половинами сегмента.
- **why_it_matters:** Панель сообщает проверяющему неверный смысл сигнала. Например, расхождение половин на 16 % отображается как 16 % рывков без ответа, хотя рывков могло вообще не быть.
- **evidence:** `packages/tracks/src/sensor-flags.ts`, функция `decoupling`: ветка половин возвращает `metric: Math.round(pct)`, ветка рывков — `metric: Math.round(share * 100)` под одним кодом. `flagMetricText` выбирает подпись только по коду. Тест `sensor-flags.test.ts` подтверждает метрику 16 для половин.
- **recommended_fix:** Использовать нейтральную подпись, не приписывающую метрике конкретный алгоритм, либо передавать тип метрики отдельным полем контракта и выбирать соответствующее пояснение. Проверить отображение обеих веток.
