### [HIGH] Новая жалоба может не изменить маркер конфликта
- **file:** apps/api/src/modules/routes/routes.repository.ts
- **location:** 548–565, 572–588
- **problem:** `recordRouteReport` увеличивает число жалоб, но обновляет `lastReportAt` через `$max` и не меняет `version`. Поэтому новая запись жалобы не обязательно изменяет поля, проверяемые при отклонении жалоб.
- **why_it_matters:** Модератор может закрыть жалобу, поступившую после просмотра карточки, без предусмотренного N7 конфликта.
- **evidence:** В `route-reports.service.ts:67–71` время фиксируется до транзакции и сохраняется при её повторах. Сценарий: запрос A получает время t1 и задерживается; B с t2 > t1 записывает жалобу; модератор открывает карточку с `lastReportAt=t2`; A завершается позднее, но `$max(t2,t1)` оставляет t2. Проверки `version` и `lastReportAt` проходят, а `closeOpen` закрывает обе жалобы. Аналогичный сбой возможен при одинаковых миллисекундах. Существующий тест N7 всегда переводит часы вперёд и этот случай не проверяет.
- **recommended_fix:** Добавить монотонную ревизию жалоб, атомарно увеличиваемую при каждой новой жалобе, передавать её в карточке и проверять при dismiss. Добавить конкурентный тест с задержанной жалобой и тест с одинаковым временем.

### [HIGH] Ошибка обновления заявки скрывается, а устаревшая карточка остаётся доступной
- **file:** apps/admin/src/features/rider-routes/RiderRouteScreen.tsx
- **location:** 185–199, 229–231, 252–274
- **problem:** Ошибки запроса обрабатываются только при отсутствии `route.data`. После загрузки карточки ошибка обновления никак не отображается. `reload` безусловно снимает баннер конфликта, даже если повторный запрос завершился ошибкой или 404.
- **why_it_matters:** Нарушен AGENTS.md §4.12: при ошибке обновления нужен баннер с повтором. После отзыва заявки автором модератор нажимает «Обновить», получает 404, но продолжает видеть прежнюю линию и кнопки решения без предупреждения; ожидаемое восстановление после конфликта RC-10 не работает.
- **evidence:** TanStack Query сохраняет прежние данные при ошибке refetch. Ветка `if (!route.data)` тогда пропускается; `await route.refetch()` по умолчанию возвращает результат с ошибкой, после чего выполняется `setStale(false)`. Таблица дополнительно получает жёсткие `isError: false` и `error: null`. Тест конфликта проверяет только успешное перечитывание.
- **recommended_fix:** Проверять результат refetch: снимать конфликт только после успеха; при сетевой ошибке/5xx сохранять данные и показывать баннер с повтором; при 404 показывать «Заявка не найдена» и убирать действия и линию, при 403 — экран отсутствия доступа. Добавить тесты ошибки обновления с уже заполненным кешем.

### [MEDIUM] Неуспешные параллельные подачи расходуют суточную квоту
- **file:** apps/api/src/modules/routes/my-route-publication.service.ts
- **location:** 49–73
- **problem:** Суточная квота списывается до условной записи маршрута и не возвращается, если запись проиграла конкурирующей подаче.
- **why_it_matters:** По RC-8 суточный лимит считает успешные подачи, а отказ 409 квоту не тратит. Несколько параллельных запросов одного маршрута могут исчерпать лимит при единственной успешной заявке.
- **evidence:** Все запросы могут пройти `assertSubmittable` и `countPendingOwn` до первой записи, затем каждый вызывает `rateLimiter.consume`. Только один `submitPublication` переводит маршрут в `pending`; остальные получают `null` и 409 на строках 71–73 без компенсации. Тест квоты выполняет запросы последовательно.
- **recommended_fix:** Обеспечить учёт только успешных подач с корректной обработкой конкуренции и сбоев; добавить тест параллельной подачи одного маршрута, после которой оставшаяся квота соответствует числу успешных переходов.
