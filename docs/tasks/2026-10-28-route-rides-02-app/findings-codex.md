### [HIGH] Повторная загрузка готового файла использует устаревший статус из кэша

- **file:** apps/app/src/features/route-rides/use-route-ride-upload.ts
- **location:** 63–79, 110–115
- **problem:** После таймаута в кэше остаётся `processing`. Если повторно загрузить тот же файл, сервер вернёт тот же `uploadId` уже со статусом `ready`, но `initialData` не заменит существующие данные запроса. При этом свежий ответ отключает запрос через `!isFinal(sent.upload)`. Эффект продолжает читать старый `upload.data`, поэтому POST проверки не происходит.
- **why_it_matters:** Повторная попытка загрузки исправного, уже обработанного файла снова заканчивается таймаутом. Нарушен AC2 — загрузка должна доводить до результата.
- **evidence:** `TrackUploadsService.accept()` возвращает существующую загрузку при повторе файла. Проверка установленного `@tanstack/query-core` через `QueryObserver` с кэшированным `processing`, `initialData: ready` и `enabled: false` дала `queryData.status: processing`, `fetchStatus: idle`. Тест загрузки `ready` использует только пустой кэш.
- **recommended_fix:** В `onUploaded` записывать свежий ответ в кэш соответствующего upload-запроса либо обрабатывать финальный `sent.upload` непосредственно. Добавить тест: таймаут → обработка сервером завершилась → повтор того же файла с тем же id → ровно один POST и переход к результату.

### [HIGH] Ошибки опроса готовности файла скрываются сообщением об обработке

- **file:** apps/app/src/features/route-rides/use-route-ride-upload.ts
- **location:** 73–80, 109–127, 150–164
- **problem:** Ошибка `getTrackUpload` никак не участвует в возвращаемом состоянии. После исчерпания ретраев GET экран продолжает показывать «Обрабатываем файл…», а через минуту сообщает, что файл ещё обрабатывается, независимо от реальной причины отказа.
- **why_it_matters:** При сетевой ошибке, 5xx или удалённой загрузке пользователь не видит ошибки чтения статуса и действия повтора. Это нарушает AGENTS.md §4.12: ошибки запросов должны быть видимы и сопровождаться повтором.
- **evidence:** Состояние вычисляется только из `file.state`, `rejected` и `own`; `upload.error`, `upload.isError` и `upload.fetchStatus` не проверяются. Таймер безусловно переводит оставшийся `processing` в `timeout`.
- **recommended_fix:** Передавать ошибку опроса в состояние интерфейса и показывать сетевой либо серверный баннер с повтором GET, сохраняя сведения о принятом файле. Добавить тесты отказа GET и успешного восстановления без повторной отправки файла.

### [HIGH] Ошибка обновления уже показанного трека полностью скрыта

- **file:** apps/app/src/features/route-rides/route-ride-map.tsx
- **location:** 84–91
- **problem:** Сообщение об ошибке и повтор отображаются только при `!data`. Если трек уже загружен, а его обновление через pull-to-refresh завершается ошибкой, пользователь не получает никакого уведомления.
- **why_it_matters:** AGENTS.md §4.12 требует сохранять показанные данные и выводить баннер с повтором при ошибке обновления. Сохранение трека реализовано, уведомление об отказе отсутствует.
- **evidence:** Условие `trackQuery.isError && !data` исключает ошибку при сохранённых данных. `RouteRideScreen` явно перезапрашивает активный track-запрос при pull-to-refresh; отдельный `AsyncContent` для этого запроса отсутствует.
- **recommended_fix:** При ошибке обновления сохранять карту и трек, дополнительно показывать баннер с повтором. Добавить тест: успешная загрузка трека → ошибка обновления → трек остаётся, баннер и повтор доступны.
