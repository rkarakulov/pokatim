### [HIGH] Повтор события после обновления заново открывает уведомление без `collapseSeq`
- **file:** apps/api/src/modules/notifications/notifications.repository.ts
- **location:** 138–150, `writeNotices`
- **problem:** Ветка `{ collapseSeq: { $exists: false } }` безусловно разрешает замену уведомлений, созданных предыдущей версией. Если до обновления событие уже обработали, уведомление прочитали и доставили, повтор того же intake после обновления совпадёт с этой веткой. Равенство `sourceEventId` больше не препятствует записи.
- **why_it_matters:** Повтор сбросит `readAt`, обновит `createdAt` и восстановит начальное состояние доставки. Пользователь повторно получит уведомление о том же событии. Это регрессия совместимости существующих документов и нарушение ADR-0017 п. 4: повтор задачи не отправляет второй push или письмо.
- **evidence:** Фильтр на строке 142 допускает любой документ без `collapseSeq`, включая документ с тем же `sourceEventId`. Через `$set: collapse.set` записываются все `fields`. `NotificationsIntakeProcessor.writeDraft` передаёт в них `readAt: null`, новое `createdAt` и результат `initialDelivery`. Новые тесты создают уведомления уже с `collapseSeq`, поэтому переход со старого формата не проверяют.
- **recommended_fix:** Для документов без `collapseSeq` отдельно сохранить дедупликацию по `sourceEventId`: повтор уже записанного события не должен менять чтение, время и доставку. При необходимости заполнить номер отдельным обновлением метаданных. Добавить интеграционный тест: существующее уведомление без `collapseSeq`, с `readAt` и завершённой доставкой → повтор исходного события → состояние уведомления и доставки не меняется.

NOT VERIFIED: `pnpm check`, интеграционные тесты и отрицательные доказательства не запускались — окружение допускает только чтение. Заявленные автором результаты независимо не подтверждены.
