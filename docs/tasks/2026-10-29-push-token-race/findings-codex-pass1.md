### [HIGH] Повтор intake после изменения райда заново открывает уведомление и сбрасывает доставку
- **file:** apps/api/src/modules/notifications/notifications.repository.ts
- **location:** 139–151, `writeNotices`
- **problem:** Сравнение только по `collapseSeq` допускает повторную запись уже обработанного события, если состояние райда успело измениться. Например: обработать `ride-rescheduled`, прочитать уведомление и завершить доставку; присоединить нового участника; повторить исходную задачу переноса. Порт вернёт увеличенный `noticeSeq`, поэтому прежнее событие снова заменит уведомление.
- **why_it_matters:** Повтор сбросит `readAt`, обновит `createdAt` и восстановит начальное состояние доставки. Пользователь повторно получит push о переносе, которого больше не происходило; новый участник также получит уведомление о старом переносе. Нарушены идемпотентность задач (§4.5 AGENTS.md) и гарантия задачи «повтор задачи ничего не меняет».
- **evidence:** `RidesRepository.join` увеличивает `noticeSeq`; `NotificationIntake.ride` каждый раз читает текущий снимок и использует его счётчик для старого события. В фильтре `writeNotices` больше нет ограничения по обработанному событию. `NotificationsIntakeProcessor.writeDraft` передаёт `readAt: null`, новое `createdAt` и `initialDelivery`, которые полностью записываются через `$set`. Новый тест повторяет задачи только при неизменном состоянии объекта и этот сценарий не обнаруживает.
- **recommended_fix:** Сохранить сравнение снимков по `collapseSeq`, но отдельно обеспечить дедупликацию уже обработанных событий: повтор одного события не должен приобретать новый снимок и повторно инициировать доставку. Добавить интеграционный тест «перенос → intake и доставка → прочтение → join → повтор исходного intake», проверяющий неизменность уведомления, отсутствие новых получателей и повторной доставки.
