Уровень — task2 (два локальных фикса модуля `notifications` + счётчик в `rides`, без новых эндпоинтов и миграций).

# 2. Goal

Закрыть два MEDIUM-follow-up Codex pass 3/4 из `docs/tasks/2026-10-27-notifications/pr.md`:

1. Поздняя регистрация токена старой сессией (выход / смена аккаунта на устройстве) не перезаписывает токен новой

2. Схлопывание уведомлений по объекту (N7) не зависит от порядка `uuidv7` внутри миллисекунды: последнее состояние

Проверка по коду (до фикса): `NotificationsRepository.registerToken` — безусловный upsert по `{ token }`;
`writeNotices` — условие `sourceEventId: { $lt }`. Оба пункта открыты.

# 3. Scope

## Push-токен (`notifications.repository.ts`, `push-tokens.service.ts`)

- Токен и endpoint принадлежат одному устройству (браузеру); текущая сессия устройства — самая поздняя из вошедших на
  нём. Регистрация сессии `S` переписывает документ токена, только если его сессия не новее `S`
  (`sessionId: { $lte: S }` в фильтре upsert; `sessionId` — `uuidv7` из `SessionService.issue`, упорядочен по времени
  входа; два входа одного устройства — последовательные запросы, не одна миллисекунда). Документ более новой сессии
  не меняется: upsert даёт дубль `push_tokens_token_unique`, повтор без изменений — тот же дубль → «устаревшая»
  регистрация, `204` без эффекта, лог `notifications.token_stale`.
- Вытеснение 11-го токена — только после фактической записи.
- Документы без `sessionId` (до привязки) — как мёртвые: любая регистрация их переписывает (`$exists: false`).

Почему не замок сессии из рекомендации Codex: клиент выходит с таймаутом (`apps/app`), поэтому отзыв сессии A может
закоммититься **после** регистрации B; замок «живая сессия + запись» тогда пропускает позднюю запись A (сессия ещё жива),
а порядок сессий — нет. Запись мёртвой сессии без новой регистрации безвредна: доставка снимает такие токены.

## Схлопывание (`notifications`, порты `rides`, `routes`)

- Черновик intake со схлопыванием — `collapse: { key, seq }`: `seq` — монотонный счётчик состояния объекта, прочитанный
  портом в том же документе, что и поля текста. Уведомление хранит `collapseSeq`; замена — только при
  `collapseSeq < seq` (или поля нет — документы до фикса); равный `seq` — тот же снимок, повтор без изменений.
- Райд: новое поле `rides.noticeSeq` (`$inc` в `join`, `leave`, `update`, `leaveAllFuture` — записи, меняющие название,
  старт, участников и `goingCount`); нет поля — `0`, без миграции. `RideNotice.noticeSeq`.
- Маршрут: существующий `publication.version` (`+1` на каждом переходе) — `RoutePublicationNotice.version`.
- `sourceEventId` уведомления — событие последней записи (как раньше), в сравнении не участвует.

# 5. Acceptance criteria

- AC1: регистрация A остановлена перед записью → выход A → регистрация B того же токена → A продолжается: владелец —
  B (`sessionId` B), ответ A — `204`. То же для подписки Web Push.
- AC2: прежние гарантии: тот же токен новым аккаунтом переходит к нему; повтор своей сессией обновляет документ;
  параллельная первая регистрация — один документ; 11-й вытесняет старейший.
- AC3: два события одного райда, второе — с меньшим `uuidv7` (та же миллисекунда, обратный порядок): после intake
  обоих в любом порядке уведомление — текст последнего состояния, снова непрочитано; повтор задачи ничего не меняет.
- AC4: `pnpm check` зелёный на изолированных БД.

# 7. Security checklist

- AuthN/AuthZ: без изменений — `AuthGuard`, `userId`/`sessionId` только из access.
- Входные данные: фильтр — примитивы после zod (`token`, `sessionId` из гарда).
- Данные наружу: ответы не меняются (`204` и для устаревшей регистрации — без оракула).
- Злоупотребления: лимит `notifications-push-token` — до записи, как раньше.
- Секреты и логи: токены и endpoint в логи не попадают (`token_stale uid=… platform=…`).
- Аудит: не нужен.

# 8. Решения

- D1: порядок сессий вместо замка (§3).
- D2: счётчик состояния объекта, читаемый портом, вместо счётчика в payload события: intake рендерит текст по
  текущему состоянию объекта, поэтому упорядочивать надо снимки состояния, а не события.
