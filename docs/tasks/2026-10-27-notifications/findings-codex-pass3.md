### [MEDIUM] Поздняя регистрация старой сессии перезаписывает токен нового аккаунта
- **file:** apps/api/src/modules/notifications/notifications.repository.ts
- **location:** `registerToken`, безусловный `$set: { userId, sessionId, ... }`
- **problem:** Регистрация A, прошедшая `AuthGuard` до выхода, может записаться после регистрации B. На одном устройстве Expo-токен обычно остаётся тем же, поэтому поздний запрос A заменяет владельца и сессию уже зарегистрированного токена B.
- **why_it_matters:** Проверка живости сессии предотвращает отправку уведомлений A, но доставка B больше не находит устройство. Доставка A удалит токен как принадлежащий мёртвой сессии. Push B перестают работать до следующей регистрации.
- **evidence:** `registerToken` обновляет документ только по `{ token }`, без повторной проверки сессии при записи. Клиент после таймаута выхода допускает новый вход, пока прежний запрос остаётся в полёте. Тест «выход A истёк по таймауту, вошёл B» использует разные токены и задерживает ответ, а не серверную запись.
- **recommended_fix:** Сериализовать проверку живой сессии и запись токена с отзывом сессии через порт identity и транзакцию с соответствующим замком. Добавить конкурентный тест: один токен, запрос A остановлен перед записью → выход A → регистрация B → продолжение A; владельцем должен остаться B.

### [MEDIUM] Неготовые квитанции блокируют обработку следующих тикетов
- **file:** apps/api/src/modules/notifications/push-receipts.ts
- **location:** `check`, строки 28–50; `NotificationsRepository.dueTickets`
- **problem:** Каждый запрос выбирает первые 1000 старейших тикетов. Если для всей первой пачки квитанций нет, цикл прекращается; следующий запуск снова выбирает ту же пачку.
- **why_it_matters:** Готовые квитанции последующих тикетов, включая `DeviceNotRegistered`, не обрабатываются до истечения первых записей. При постоянном потоке тикеты могут дожидаться TTL и удаляться без проверки; недействительные токены остаются зарегистрированными.
- **evidence:** `dueTickets` сортирует по `{ createdAt: 1, _id: 1 }` и применяет `limit`, курсора нет. Условие `done.length === 0` завершает обход, необработанные записи остаются первыми.
- **recommended_fix:** Добавить курсор обхода по `(createdAt, _id)` либо срок следующей проверки тикета, чтобы неготовая пачка не закрывала доступ к следующим. Проверить сценарий: первые 1000 квитанций отсутствуют, у следующего тикета готов `DeviceNotRegistered`.

### [LOW] Конкурентная первая вставка может потерять более новое схлопываемое событие
- **file:** apps/api/src/modules/notifications/notifications.repository.ts
- **location:** `writeNotices`, ветка `collapseKey`, обработка `MongoBulkWriteError`
- **problem:** Две первые параллельные обработки событий A < B могут одновременно не найти документ. Если A вставится первой, вставка B получит ошибку уникальности, которую код безусловно считает повтором или устаревшим событием.
- **why_it_matters:** Более новое событие B теряется: `sourceEventId`, непрочитанность и состояние доставки остаются от A. Требование N7 выполняется не во всех конкурентных сценариях.
- **evidence:** Upsert использует `sourceEventId: { $lt: sourceEventId }`; ошибка `notifications_collapse_unique` поглощается без повторного условного обновления. Находка предыдущего прохода остаётся неисправленной.
- **recommended_fix:** После конфликта уникальности повторить условное обновление соответствующего документа без upsert. Добавить тест конкурентной первой записи разных событий одного `collapseKey`.
