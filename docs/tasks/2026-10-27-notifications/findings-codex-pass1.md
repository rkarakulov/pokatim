### [HIGH] Канал Android создаётся только после получения разрешения
- **file:** apps/app/src/features/notifications/push.ts
- **location:** requestPushPermission, строки 48–51; obtainPushToken, строки 83–88
- **problem:** Системный запрос разрешения выполняется без создания канала. Единственный вызов `setNotificationChannelAsync` находится после проверки `status === 'granted'`.
- **why_it_matters:** На новой установке Android 13+ возникает циклическая зависимость: для показа запроса нужен канал, а приложение создаёт канал только после разрешения. Включение push через предусмотренную строку не работает; нарушены AC8 и §4.13.
- **evidence:** `requestPushPermission()` сразу вызывает `requestPermissionsAsync()`, а `obtainPushToken()` возвращает `null` до создания канала при отсутствии разрешения. [Документация Expo](https://docs.expo.dev/versions/latest/sdk/notifications/#android) прямо указывает необходимость предварительного создания канала.
- **recommended_fix:** По нажатию «Включить push» сначала создать Android-канал `default`, затем запросить разрешение. Добавить тест первого включения на Android, проверяющий порядок операций.

### [HIGH] Параллельные изменения настроек могут перезаписывать друг друга
- **file:** apps/app/src/app/settings/notifications.tsx
- **location:** SettingsForm, строки 94–100, 116–159
- **problem:** Во время сохранения тумблеры и выбор часов остаются доступны. Каждое действие отправляет полный объект отдельным запросом, без сериализации.
- **why_it_matters:** Пользователь выключает push гонок, затем письма райдов. Второй запрос содержит оба изменения, но первый может завершиться последним и вернуть прежнее значение писем. Сервер и кеш молча теряют последнее намерение пользователя. Также нарушено требование §4.12 о недоступности управления на время мутации.
- **evidence:** `save` безусловно вызывает `update.mutate(next)`; `Toggle` и `HourPicker` не получают состояние блокировки. `useUpdateNotificationSettings.onSuccess` записывает каждый завершившийся ответ в кеш, а сервер выполняет полную замену через `saveSettings`.
- **recommended_fix:** Блокировать все элементы формы на время сохранения либо сериализовать изменения с объединением последнего состояния. Добавить тест двух изменений с обратным порядком завершения запросов.

### [HIGH] Незавершённая регистрация токена может восстановить push после выхода
- **file:** apps/app/src/features/notifications/push-registration.ts
- **location:** registerDevicePush, строки 25–30; revokeDevicePushToken, строки 40–55
- **problem:** Регистрация токена и выход выполняются независимо. Токен сохраняется локально только после ответа регистрации, а снятие использует исключительно уже сохранённый токен.
- **why_it_matters:** Если регистрация уже прошла `AuthGuard`, но ещё не записала токен, выход видит пустое хранилище и пропускает снятие. Затем регистрация записывает токен на сервере уже после выхода. Аккаунт остаётся живым, поэтому доставка продолжает отправлять его уведомления на устройство следующего пользователя. Это нарушает гарантию снятия токена при выходе.
- **evidence:** `if (!token) return` прекращает снятие без ожидания текущей регистрации. Серверный `registerToken` делает безусловный upsert владельца. Проверка сессии после ответа в `withAccessToken` предотвращает применение результата клиентом, но не отменяет серверную запись.
- **recommended_fix:** Согласовать жизненный цикл регистрации и выхода: запретить новые регистрации при начале выхода, сериализовать текущую регистрацию со снятием и гарантировать очистку поздней серверной записи. Добавить конкурентный тест с остановкой регистрации перед upsert и выходом в этот момент.

### [MEDIUM] Захват письма допускает истёкшие уведомления
- **file:** apps/api/src/modules/notifications/notifications.repository.ts
- **location:** claimEmail, строки 355–364
- **problem:** В фильтре захвата письма отсутствует `expireAt > now`, хотя аналогичный фильтр push проверяет срок хранения.
- **why_it_matters:** Задача доставки или регламент могут отправить письмо по уведомлению, которое уже истекло и недоступно в центре, пока TTL ещё не удалил документ.
- **evidence:** `claimEmail` проверяет только `_id` и состояние доставки. `stuckEmails` также выбирает истёкшие документы. Правило `.claude/rules/db.md` требует проверять истечение сервером: TTL служит только уборкой.
- **recommended_fix:** Добавить проверку `expireAt` в захват письма и выборки регламента. Покрыть случай `expireAt === now`: письмо не отправляется.
