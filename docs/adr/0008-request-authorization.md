# 0008. Авторизация запросов: access JWT + живая сессия; авто-refresh в приложении

- Статус: Accepted
- Дата: 2026-10-25

## Контекст

Слайсы онбординга 1–3 выдают сессию (access JWT 15 мин + ротируемый refresh, ADR-0005), но эндпоинтов, требующих
входа, не было. Первый такой эндпоинт — опрос «Что вас привело?» (`docs/tasks/2026-10-25-onboarding-04-survey-geo`).
Слайс 3 оставил открытым, проверяет ли сервер только подпись access или и живость сессии `sid`: выход, сброс пароля
и reuse detection отзывают сессию сразу, а access живёт до 15 мин. Клиенту нужен единый способ передать access и
обновить его до истечения или после 401, не трогая публичные эндпоинты.

## Решение

**Сервер (`apps/api/src/modules/identity`):**

- `AccessTokenVerifier` — единственная проверка access: только HS256, `iss`/`aud` проекта, `exp` по `CLOCK`,
  обязательные `sub` и `sid` (UUID после zod). Заголовок — строго `Bearer <jwt>`, длина ≤ 2048, иначе отказ до jose.
- `AuthGuard` — JWT **и** живость сессии: `sessions` по `_id = sid` с `userId = sub`, `revokedAt: null`,
  `expiresAt > now`, и `users` по `_id = sub` с `deletedAt: null` (два чтения по `_id`). Любой отказ — один и тот же
  `401 UNAUTHORIZED`, без лога. Пользователь запроса — только `@CurrentUser()` из access, не из тела или пути.
- Другие модули подключают `AuthGuard` через `modules/identity/index.ts` (`imports: [IdentityModule]`); коллекции
  identity сами не читают.

**Приложение (`apps/app/src/features/auth/authorized.ts`):**

- Access передаётся явно (`Authorization: Bearer`) только в методы api-client, требующие входа
  (`getOnboardingStatus(accessToken)`, …); глобального `getAccessToken` в клиенте нет.
- `withAccessToken(call)`: access истекает в ближайшие 60 с — обновление до запроса; ответ 401 — одно обновление
  и один повтор. Обновление — single-flight через `refreshAccess` платформы под замком сессии (native — ротация refresh
  из SecureStore, web — refresh по cookie под Web Lock). Refresh 401 — локальный выход (`returning`, гард ведёт на
  «Вход»); сеть, 429, 5xx — ошибка запроса, сессия остаётся.

## Альтернативы

- **Только JWT (stateless):** быстрее, но отозванная сессия (выход, сброс пароля, reuse) ещё до 15 мин читает и пишет
  данные. Нет.
- **JWT + кеш живости сессии в Redis (≤ 60 с):** оптимизация без нагрузки; инвалидация кеша при отзыве — лишняя
  сложность сейчас. Отложено (пересмотр ниже).
- **`getAccessToken` в `createApiClient`:** Bearer уходил бы во все запросы, включая публичные и cookie-эндпоинты, и
  замыкал цикл импорта `api` ↔ стор сессии; refresh по 401 всё равно нужен сверху. Нет.

## Последствия

- Отзыв сессии (выход, сброс пароля, reuse detection, будущее удаление аккаунта) действует на авторизованные запросы
  сразу. Гонка «запрос ↔ отзыв» принята: запрос, прошедший проверку до коммита отзыва, завершается.
- Стоимость — два чтения по `_id` на авторизованный запрос. Пересмотреть при нагрузке: кеш «сессия жива» в Redis на
  ≤ 60 с с инвалидацией при отзыве.
- Фоновая ротация по `AppState` не нужна: обновление перед авторизованным запросом её покрывает.
- Кандидаты в app-foundation (с переносом identity в базу, F6): `AuthGuard`, «авторизованный запрос с single-flight
  refresh» в `api-client-core`.
