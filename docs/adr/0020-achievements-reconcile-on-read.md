# 0020. Достижения: выдача сверкой при чтении

- Статус: Proposed
- Дата: 2026-10-29
- Задача: `docs/tasks/2026-10-29-achievements` (PR A)

## Контекст

Райдер получает достижения за гонки, заезды по маршрутам и кофе-райды (`docs/product/profile.md`, A1–A8). Факты
живут в трёх модулях-владельцах (`results` — протоколы, `route-rides` — заезды, `rides` — райды) и меняются задним
числом: DQ и новая ревизия протокола, удаление активности, снятие маршрута, отмена и скрытие райда. Достижение должно
появиться один раз (вспышка), исчезнуть молча, когда факт пропал, и вернуться без повторной вспышки.

Канон (AGENTS.md §4.5): доменные события между модулями — outbox, тяжёлое — worker. Но outbox базы отправляет тип
события в одну очередь (DV-1 слайса 08), а у `results` и `rides` подписчик уже есть (`notifications`); половина
фактов («активность удалена», «маршрут снят») событий не порождает вовсе.

## Решение

1. **Выдача — проекция фактов, сверяемая при чтении.** `GET /v1/achievements` читает факты райдера через порты
   владельцев (`RIDER_RESULTS`, `RIDER_ROUTE_RIDES`, `RIDER_RIDES`), выводит заработанные достижения чистыми функциями
   (`achievements.policy.ts`) и сверяет с сохранёнными выдачами: новое — выдать, пропавшее — отозвать (`revokedAt`),
   вернувшееся — восстановить с прежним `seenAt`, сменившийся объект — обновить. Устойчивое состояние — GET без
   записей.
2. **Своя коллекция, без транзакций.** `achievement_grants` — один документ на `(userId, code)` (уникальный индекс);
   каждая запись — одна условная операция над одним документом; дубль параллельной вставки — `isDuplicateKey`, не
   ошибка. Параллельные GET одного райдера сходятся к одному состоянию (int-тест с отрицательными доказательствами).
3. **«Первая сверка» — маркер `achievement_syncs`**, который ставится **после** выдач первой сверки: всё, найденное
   впервые, выдаётся сразу просмотренным (тихая ретро-выдача, A3). Порядок «выдачи → маркер» обязателен: кто увидел
   маркер, тот видит и тихие выдачи.
4. **Ни worker, ни очередей, ни outbox, ни регламента.** Сверка — ≤ ~10 запросов по индексам без разбора треков и
   рендера; лимит `achievements-read:<uid>` 60/мин. Публичный список (`GET /v1/riders/:publicId/achievements`) — те
   же правила над протоколами, без записи.

## Альтернативы

- **Подписка на события outbox** — тип события уходит в одну очередь, подписчик у `results`/`rides` занят
  (`notifications`); у удаления активности и снятия маршрута событий нет. Нужен fan-out outbox в app-foundation
  (follow-up ADR-0017) и события в трёх модулях.
- **Регламент в worker** (как `standings`, DV-1) — скан всех райдеров по расписанию: стоимость растёт с базой, а
  выдача нужна только тем, кто открыл приложение; задержка вспышки до прогона.
- **Транзакция на весь план / замок на пользователя в Redis** — конфликты записи и повторы у двух GET без выигрыша
  (исход один), лишняя инфраструктура.

## Следствия

- ~~Нет push «новое достижение» без отдельного механизма~~ — снято «Дополнением: push» ниже (событие outbox при
  выдаче; серверная сверка — PR N2).
- Каждый GET читает протоколы, заезды и райды райдера: лимиты портов (2000 строк, лог усечения), клиент — `staleTime`
  и запрос на старте и возврате приложения.
- Запись в GET (`no-store`, под `AuthGuard`) — сознательно; запись ограничена 9 документами на пользователя.
- Eventual consistency объекта: устаревший параллельный GET может записать объект своего чтения — следующая сверка
  исправит; `seen` не затрагивается.
- Новый код каталога — правило в `ACHIEVEMENT_RULES` (исчерпывающий `satisfies`) и код в конец `ACHIEVEMENT_CODES`;
  у райдеров, уже прошедших первую сверку, он вспыхнет — это и нужно для нового достижения.
- Новый модуль с данными пользователя: порт стирания `AchievementErasure`, шаг `achievements` в
  `AccountErasureService` (ADR-0015).

## Дополнение: уровни (achievements-levels, 2026-10-30)

Уровни «Бронза / Серебро / Золото» у трёх счётных кодов (`docs/product/profile.md` L1–L7) модель не меняют.

- **Уровень — ещё одно поле проекции** (`level`, ранг 1–3; разовые — `null`), как `object`/`factAt`: пересчитывается
  каждой сверкой, другой ранг — `refresh`. Пороги — `ACHIEVEMENT_LEVEL_TARGETS` в `@pokatim/contracts` (одна таблица
  для политики, карточки и приложения); наружу — строка `bronze | silver | gold`.
- **«Показано» — `seenAt` + монотонный `seenLevel`**: `seen` = `seenAt != null && seenLevel >= level` ответа
  (уровень из фактов запроса, а не сохранённый — устаревший параллельный план мог записать меньший). Понижение и
  возврат на показанный уровень не вспыхивают; повышение — `seen: false`.
- **`POST seen` — одна условная операция update pipeline:** `seenLevel = max(seenLevel, level)` из того же документа в
  момент записи; клиент уровень не присылает, схема запроса прежняя. Окно «повышение между GET и `POST seen`» отметит
  новый уровень показанным, не показав его, — принято (секунды, один пользователь). Обратное окно: устаревшая
  параллельная сверка записала меньший `level` перед `POST seen` — `seenLevel` останется ниже показанного, и тот же
  уровень вспыхнет ещё раз после перезапуска; принято (редко, без потери данных).
- **Документы v1 — без миграции и бэкфилла:** нет `level`/`seenLevel` ≡ 1 на чтении и в pipeline (`$ifNull`); индексы
  прежние.
- **Вспышка повышения у сверившихся райдеров:** первая сверка после выкладки у райдера с 15+ фактами — одна вспышка
  «Новый уровень» на текущем уровне (как новый код у сверившихся); первая сверка райдера — по-прежнему тихо на любом
  уровне. Старая сборка увидит повышение как «Новое достижение» прежнего кода — раз на повышение.
- **Карточка сторис:** уровень — в хэше входов и `renderVersion` (3); ключи Redis и задача рендера не меняются.

## Дополнение: сезонные (achievements-seasonal, 2026-10-31)

Сезонные достижения («Чемпион сезона», «Призёр сезона», «Сезон в зачёте» — `docs/product/profile.md` S1–S8) модель не
меняют: выдача — проекция фактов, сверка при `GET /v1/achievements`, каждая запись — одна условная операция над одним
документом без транзакций.

- **Отдельная коллекция `achievement_season_grants`** — один документ на `(userId, code, seasonId)`, уникальный индекс
  `achievement_season_grants_user_code_season_unique` (миграция `0043_achievements_seasonal`, только expand). Почему не
  расширение ключа `achievement_grants` (HG-S1): пришлось бы удалить индекс `achievement_grants_user_code_unique` —
  деструктивная операция; документы v1 и их индекс не меняются. Писатель обеих коллекций и маркера — тот же
  `AchievementsRepository`.
- **Общий маркер первой сверки** ставится после выдач обеих коллекций: увидевший маркер видит и тихие выдачи.
- **Факты — порт `standings` `RIDER_SEASON_STANDINGS`** (снимок рейтинга, без пересчёта): строки райдера по
  завершённым сезонам, число ячеек с местом, статус сезона `final | pending`. `achievements` чужих коллекций не читает;
  ребро `achievements → standings` — только в `AchievementsModule`.
- **Только `final`-сезоны меняют выдачи:** последний день прошёл, нет опубликованной гонки с коридором без протокола
  (RC-S2), отпечаток снимка равен отпечатку источника (`StandingsSource` — тот же расчёт, что у регламента). Сезон в
  `pending` — ни вставки, ни отзыва; видимая выдача остаётся в своём списке, публичный список её на это время не
  показывает (без чтения выдач, RC-S5). Отзыв и возврат — как A4, `refresh` нет (дата завершённого сезона неизменна).
- **`POST seen`:** `{ codes?, seasonal? }` — две независимые атомарные операции; `{ codes }` старых сборок работает как
  прежде.
- **Бюджет запросов GET** — ≤ ~16 (было ≤ ~10): +3…6 запросов по существующим индексам; без сезонных итогов — +2.
- **RC-S10:** первая сверка райдера в окне `pending` не выдаёт сезонные этого сезона; они появятся позже — со вспышкой
  (A3 нарушается на секунды-минуты).

## Дополнение: push (achievements-push N1, 2026-10-31)

Задача — `docs/tasks/2026-10-31-achievements-push` (PR N1 — уведомление из сверки при чтении; серверная сверка в
worker — PR N2, «Дополнение: серверная сверка» ниже).

- **Сверка одна:** `AchievementsReconciler.reconcile(userId, origin)` (`AchievementsSyncModule`) — факты → планы →
  запись → маркер → итог для ответа; `AchievementsService.sync` — лимит `achievements-read:<uid>` и сборка ответа
  поверх него (`origin: 'read'`). Тип `'server'` готов для worker (PR N2), копий планов и условий нет.
- **Уведомление — выдача, которая вспыхнула бы, и о её уровне ещё не сообщали:** вставка не в первой сверке
  (несезонная — с уровнем, разовые и сезонные — без); `refresh`/`restore` несезонной — только если новый ранг выше
  `notifiedLevel` и не показан (`noticeDue`, чистая функция политики; восстановление на более высоком уровне — тоже,
  RC-P3); первая сверка (A3), сезонный `restore`, отзывы, понижение, смена объекта — тихо.
- **`achievement_grants.notifiedLevel`** (ранг 1–3, монотонно `$max`) — наибольший объявленный уровень. Ставится каждой
  вставкой (`= level`, в первой сверке — тоже) и каждым `refresh`/`restore` (`$max(notifiedLevel ?? level ?? 1, L)`);
  у документов до выката поля нет — ≡ сохранённый уровень (ретро-уведомлений нет). Без миграции и индекса.
- **Транзакции только для шагов, которые могут дать уведомление** (AGENTS §4.5): вставка не в первой сверке —
  `insertOne` + `MongoOutboxWriter.append` в `MongoTransactions.run`, дубль уникального индекса обрывает транзакцию и
  ловится снаружи `run` (откат, события нет); `refresh`/`restore` — `findOneAndUpdate` (pipeline, `returnDocument:
  'before'`) первой операцией, решение о событии — по документу до записи в той же транзакции. Параллельные сверки
  одного райдера конфликтуют по документу выдачи → драйвер повторяет колбэк → повтор видит закоммиченный документ или
  `notifiedLevel` → событие одно (P3). Замков и чтения-проверки нет. Отзывы, сезонные восстановления, первая сверка,
  маркер и `POST seen` — прежние одиночные операции без транзакции (RC-2 для них в силе).
- **Событие** `achievements.grant-noticed` (`{ grant: 'fact' | 'season', grantId, level, origin }` — без `userId` и
  текстов); маршрут объявляет `notifications`, поля уведомления — порт `ACHIEVEMENT_NOTICES` (выдача по `_id`: стёрта —
  `gone`; отозвана, ранг ниже, факт пропал, сезонный код не заработан по `final`-исходу или сезон в `pending` — `state`;
  название — факты `AchievementFactsReader` или итог `RIDER_SEASON_STANDINGS.outcomesOf`). Вторая линия идемпотентности — схлопывание `achievement:<grantId>` по рангу.
- **Канал:** `origin: 'read'` — запись в центре без push (райдер видит вспышку; уведомление непрочитано, RC-P6);
  `'server'` — центр и push по группе «Достижения» (ADR-0017). Вспышка push-ем не отменяется (A5).

## Дополнение: серверная сверка (achievements-push N2, 2026-10-31)

- **Зачем:** push без открытия приложения (P2). Сверка та же — `reconcile(userId, 'server')` в worker (центр + push).
- **Регламент по курсорам, не события:** fan-out outbox нет (ADR-0017 п. 5), `results.*`/`rides.*` уже заняты
  `notifications-intake`, у «заезд засчитан» и «сезон подведён» событий нет. Очередь `achievements-sync`
  (`AchievementsWorkerModule`): `achievements.sweep` каждую минуту (Минск) + `achievements.sweep.boot`, один прогон за
  раз (замок-аренда Redis `achievements:sweep:lock`: продление своим токеном перед каждым шагом, курсоры пишет только
  владелец — проверка токена и запись одним Lua; аренда потеряна — прогон прекращается без записи курсоров,
  `achievements.sweep_lease_lost`); задачи `achievements.rider` (`ach-rider-<uid>-<прогонMs>`, 3 попытки,
  экспоненциальная пауза; последняя — лог `achievements.server_sync_failed`, failed-набор).
- **Источники — по одному методу портов владельцев**, окно `(курсор, until]` по keyset (`changed-since.ts`), ≤ 500
  строк за прогон, `until = now − 2 мин` (запас на коммит): ревизии протоколов (`RIDER_RESULTS.revisedRidersAfter` —
  журнал по uuidv7 `_id`, получатели страницы — один запрос по парам `(raceId, revision)`), прошедшие райды
  (`RIDER_RIDES.startedRidersAfter`, `until = now − 3 ч` — push после поездки, RC-P1), засчитанные заезды
  (`RIDER_ROUTE_RIDES.passedRidersAfter` — по моменту записи итога `updatedAt`, а не `checkedAt`: тот берётся до
  ожидания семафора разбора; индекс `0044_route_rides_passed_idx`), итоги сезонов
  (`RIDER_SEASON_STANDINGS.settledRidersAfter` — момент `max(computedAt, endsBefore, последняя отмена гонки с
  коридором)` завершённого сезона: отмена гонки, ждавшей протокола, делает итог полным без пересчёта снимка —
  `SEASON_RACES.lastCancelledAt`; строки снимка по `userId`). Полного скана райдеров нет.
- **Кого сверять:** живые аккаунты (`liveUserIds`, RC-P7) ∩ с маркером первой сверки (`syncedAmong`) — первая сверка
  остаётся тихой при открытии приложения. Курсоры (`achievements:cursor:<source>`) двигаются после постановки задач;
  сбой источника — его курсор стоит, прогон падает после остальных.
- **Push — «не больше одного» (RC-P9):** коммит факта позже `settleMs`, задача не поставилась, потерян курсор — push
  нет, запись в центре появится при следующем GET (`origin: 'read'`). Нет курсора (первый запуск и потеря Redis
  неразличимы) — окно с `until − 10 мин`. Одно уведомление на выдачу гарантируют транзакция и схлопывание.
- **RC-P7:** задача, начатая до закрытия аккаунта, может записать выдачу после шага стирания `achievements` —
  осиротевшие выдачи без ПДн (кроме `userId`); уведомления не будет (`liveUserIds` в intake). Принято.
