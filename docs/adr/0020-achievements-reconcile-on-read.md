# 0020. Достижения: выдача сверкой при чтении

- Статус: Proposed
- Дата: 2026-10-29
- Задача: `docs/tasks/2026-10-29-achievements` (PR A)

## Контекст

Райдер получает достижения за гонки, заезды по маршрутам и кофе-райды (`docs/product/profile.md`, A1–A8). Факты
живут в трёх модулях-владельцах (`results` — протоколы, `route-rides` — заезды, `rides` — райды) и меняются задним
числом: DQ и новая ревизия протокола, удаление активности, снятие маршрута, отмена и скрытие райда. Достижение должно
появиться один раз (вспышка), исчезнуть молча, когда факт пропал, и вернуться без повторной вспышки.

Канон (AGENTS.md §4.5): доменные события между модулями — outbox, тяжёлое — worker. Но outbox базы отправляет тип
события в одну очередь (DV-1 слайса 08), а у `results` и `rides` подписчик уже есть (`notifications`); половина
фактов («активность удалена», «маршрут снят») событий не порождает вовсе.

## Решение

1. **Выдача — проекция фактов, сверяемая при чтении.** `GET /v1/achievements` читает факты райдера через порты
   владельцев (`RIDER_RESULTS`, `RIDER_ROUTE_RIDES`, `RIDER_RIDES`), выводит заработанные достижения чистыми функциями
   (`achievements.policy.ts`) и сверяет с сохранёнными выдачами: новое — выдать, пропавшее — отозвать (`revokedAt`),
   вернувшееся — восстановить с прежним `seenAt`, сменившийся объект — обновить. Устойчивое состояние — GET без
   записей.
2. **Своя коллекция, без транзакций.** `achievement_grants` — один документ на `(userId, code)` (уникальный индекс);
   каждая запись — одна условная операция над одним документом; дубль параллельной вставки — `isDuplicateKey`, не
   ошибка. Параллельные GET одного райдера сходятся к одному состоянию (int-тест с отрицательными доказательствами).
3. **«Первая сверка» — маркер `achievement_syncs`**, который ставится **после** выдач первой сверки: всё, найденное
   впервые, выдаётся сразу просмотренным (тихая ретро-выдача, A3). Порядок «выдачи → маркер» обязателен: кто увидел
   маркер, тот видит и тихие выдачи.
4. **Ни worker, ни очередей, ни outbox, ни регламента.** Сверка — ≤ ~10 запросов по индексам без разбора треков и
   рендера; лимит `achievements-read:<uid>` 60/мин. Публичный список (`GET /v1/riders/:publicId/achievements`) — те
   же правила над протоколами, без записи.

## Альтернативы

- **Подписка на события outbox** — тип события уходит в одну очередь, подписчик у `results`/`rides` занят
  (`notifications`); у удаления активности и снятия маршрута событий нет. Нужен fan-out outbox в app-foundation
  (follow-up ADR-0017) и события в трёх модулях.
- **Регламент в worker** (как `standings`, DV-1) — скан всех райдеров по расписанию: стоимость растёт с базой, а
  выдача нужна только тем, кто открыл приложение; задержка вспышки до прогона.
- **Транзакция на весь план / замок на пользователя в Redis** — конфликты записи и повторы у двух GET без выигрыша
  (исход один), лишняя инфраструктура.

## Следствия

- Нет push «новое достижение» без отдельного механизма: выдача появляется только при запросе райдера (вспышка — при
  открытии приложения). Push — follow-up с событиями или регламентом.
- Каждый GET читает протоколы, заезды и райды райдера: лимиты портов (2000 строк, лог усечения), клиент — `staleTime`
  и запрос на старте и возврате приложения.
- Запись в GET (`no-store`, под `AuthGuard`) — сознательно; запись ограничена 9 документами на пользователя.
- Eventual consistency объекта: устаревший параллельный GET может записать объект своего чтения — следующая сверка
  исправит; `seen` не затрагивается.
- Новый код каталога — правило в `ACHIEVEMENT_RULES` (исчерпывающий `satisfies`) и код в конец `ACHIEVEMENT_CODES`;
  у райдеров, уже прошедших первую сверку, он вспыхнет — это и нужно для нового достижения.
- Новый модуль с данными пользователя: порт стирания `AchievementErasure`, шаг `achievements` в
  `AccountErasureService` (ADR-0015).

## Дополнение: уровни (achievements-levels, 2026-10-30)

Уровни «Бронза / Серебро / Золото» у трёх счётных кодов (`docs/product/profile.md` L1–L7) модель не меняют.

- **Уровень — ещё одно поле проекции** (`level`, ранг 1–3; разовые — `null`), как `object`/`factAt`: пересчитывается
  каждой сверкой, другой ранг — `refresh`. Пороги — `ACHIEVEMENT_LEVEL_TARGETS` в `@pokatim/contracts` (одна таблица
  для политики, карточки и приложения); наружу — строка `bronze | silver | gold`.
- **«Показано» — `seenAt` + монотонный `seenLevel`**: `seen` = `seenAt != null && seenLevel >= level` ответа
  (уровень из фактов запроса, а не сохранённый — устаревший параллельный план мог записать меньший). Понижение и
  возврат на показанный уровень не вспыхивают; повышение — `seen: false`.
- **`POST seen` — одна условная операция update pipeline:** `seenLevel = max(seenLevel, level)` из того же документа в
  момент записи; клиент уровень не присылает, схема запроса прежняя. Окно «повышение между GET и `POST seen`» отметит
  новый уровень показанным, не показав его, — принято (секунды, один пользователь).
- **Документы v1 — без миграции и бэкфилла:** нет `level`/`seenLevel` ≡ 1 на чтении и в pipeline (`$ifNull`); индексы
  прежние.
- **Вспышка повышения у сверившихся райдеров:** первая сверка после выкладки у райдера с 15+ фактами — одна вспышка
  «Новый уровень» на текущем уровне (как новый код у сверившихся); первая сверка райдера — по-прежнему тихо на любом
  уровне. Старая сборка увидит повышение как «Новое достижение» прежнего кода — раз на повышение.
- **Карточка сторис:** уровень — в хэше входов и `renderVersion` (3); ключи Redis и задача рендера не меняются.
