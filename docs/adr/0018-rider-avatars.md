# 0018. Аватары райдеров: перекодирование sharp в HTTP-обработчике, байты в MongoDB, публичная отдача по случайному id

- Статус: Accepted
- Дата: 2026-10-28
- Задача: `docs/tasks/2026-10-28-rider-profile` (PR A)

## Контекст

У профиля райдера появляется фото (`docs/product/profile.md`, R1–R10). Фото — ПДн и UGC: в исходнике бывают EXIF с
GPS-координатами, большие и битые файлы, форматы с историей уязвимостей декодеров. Фото видно другим в публичном
профиле (только при имени и согласии) и в приложении. Файлы пользователей по ADR-0011 «наружу не выдаются», S3 и CDN
до прода нет, тяжёлая работа по `pokatim-backend.md` — в worker.

## Решение

1. **Обработка — `sharp` в HTTP-обработчике (RC-A1, исключение из «тяжёлое — в worker»).** Перекодирование аватара —
   синхронное и ограниченное: вход ≤ 10 МиБ (`readLimited`, свои таймауты тела — тишина 10 с, всё тело 60 с), ≤ 25 Мп
   (`limitInputPixels` + проверка заголовка), `timeout` 10 с, слот приёма — **1 на процесс** и 1 на пользователя
   (`UploadSlots`; слот берётся до списания лимита), лимит 20 загрузок в час; декодирование идёт в пуле libvips (libuv),
   не в event loop; `sharp.cache(false)`, `concurrency(1)`. `failOn: 'error'` — **ослабление** относительно дефолта
   sharp (`warning`): JPEG телефонов с предупреждениями libvips принимаются, отказ — только на ошибках декодера;
   поверхность libvips та же.
   **Память (ревью PR A, MEDIUM-1).** Замер скриптом ревьюера (sharp 0.35.5, macOS arm64, тот же конвейер `autoOrient →
   extract → resize`, JPEG с orientation 6): 40 Мп — одна обработка +136…141 МБ RSS, две параллельные +281…286 МБ;
   25 Мп (6250×4000) — одна +93 МБ, две +175…185 МБ. У контейнера `api` лимит 512 МБ — выбраны 25 Мп и 1 слот на
   процесс: пик обработки ≈ +93 МБ плюс тело ≤ 2×10 МиБ. Shrink-on-load JPEG (`resize` до `extract`) не применён:
   обрезка — в координатах полного изображения, точность квадрата важнее; кадры 48 Мп клиент уменьшает при обрезке
   (PR B). Пик RSS в образе `linux/amd64` (glibc) — проверить до прода (`pr.md`).
   «Рендер в HTTP-обработчике» в красных флагах — Skia, ffmpeg, OG-картинки; аватар туда не входит. Очередь отклонена:
   исходник с GPS пришлось бы хранить до обработки, а клиенту — опрашивать статус.
2. **Конвейер (`avatar-image.ts`).** Формат — по сигнатуре (JPEG, PNG, WebP; иначе `415 AVATAR_FORMAT_UNSUPPORTED`),
   `metadata().format` обязан совпасть с сигнатурой. Поворот по EXIF (`autoOrient`), квадрат по намерению клиента
   (доли `x, y, size` ориентированного изображения; без них — центр; сервер ограничивает рамками, сторона < 64 px —
   `422 AVATAR_INVALID`), 512×512 JPEG. Метаданные не пишутся (`withMetadata`/`withExif`/`keepMetadata` не
   вызываются): EXIF, GPS, XMP и ICC стираются. Не декодируется, больше 25 Мп, таймаут — `422 AVATAR_INVALID`; в лог —
   `uid`, размер, формат, исход, без сообщения libvips.
3. **Хранение — MongoDB, коллекция `profile_avatars`.** Документ ≈ 30–90 КБ (`Binary` JPEG), `_id` — `randomToken`
   (32 байта, base64url), индекс `{ userId }`. Один аватар на пользователя: замена в одной транзакции — вставка нового,
   `profiles.avatarId`, удаление прежнего; удаление фото — `POST /v1/profile/avatar/delete` (RC-A5: в API удаление —
   `POST …/delete`). Исходник не хранится. Единственный писатель — `ProfileAvatarRepository`.
4. **Отдача — `GET /v1/avatars/:id` без входа (исключение из ADR-0011).** `PublicReadGuard`, `image/jpeg`, `public,
   max-age=31536000, immutable` (байты по id не меняются — замена даёт новый id), `X-Content-Type-Options: nosniff`,
   `Content-Security-Policy: default-src 'none'; sandbox`; заголовки — после чтения, 404 — JSON без `immutable`.
   Согласие на отдаче не проверяется (RC-A2): id непредсказуем, видевший фото мог сохранить его и так, свой аватар
   нужен и без согласия; удаление или замена фото отзывает URL (404).
5. **Удаление аккаунта** — `ProfileErasure.erase` стирает `profile_avatars` по `userId` до документа профиля
   (ADR-0015, шаг `profile`).

## Последствия

- `sharp` — runtime-зависимость `apps/api`; бинарники `@img/sharp-*` ставятся как optionalDependencies (lockfile
  содержит все платформы, ставится своя), `infra/docker/runtime-deps.mjs` копирует их в образ. Проверка образа —
  `docker build --platform linux/amd64 --target api` и `node -e "require('sharp')"`.
- CVE libvips — обновлять `sharp` (Dependabot); вход ограничен сигнатурой, пикселями и выводом только JPEG.
- Один слот на процесс: одновременная загрузка второго пользователя получает `429` с `retryAfterSec: 5` (клиент
  повторяет); медленная отправка держит слот не дольше 60 с.
- Пул libuv (4 потока) делят sharp, `crypto`, `fs`, `dns`: 1 слот × ≤ 10 с занимает до четверти — метрика времени
  ответа входа под нагрузкой загрузок — follow-up.
- После отзыва согласия фото остаётся доступным по уже известному URL (RC-A2); перевыпуск id при отзыве — follow-up
  вместе с модерацией фото. Браузеры с `immutable` держат удалённое фото до очистки кэша.
- S3, подписанные URL и CDN — вне рамок; при переезде меняется только репозиторий и отдача.
