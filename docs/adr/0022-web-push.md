# 0022. Web Push в PWA — второй транспорт канала push

- Статус: Accepted
- Дата: 2026-10-29
- Задача: `docs/tasks/2026-10-29-web-push`
- Снимает: ADR-0017 п. 1 («Web push — нет»), AGENTS §1 и §4.9 (web push)

## Контекст

В web (PWA) уведомления видны только в центре и на колокольчике (ADR-0017). Установленная PWA на Android, desktop
Chrome/Edge и iOS 16.4+ (только установленная на экран «Домой») умеет Web Push (RFC 8030) через push-сервис браузера.

## Решение

1. **Тот же канал, другой транспорт.** Web Push — не отдельная система: событие → уведомление → настройки группы,
   тихие часы, лимит 20/ч, сводка, захват — как у Expo (ADR-0017). Подписка браузера — документ `push_tokens`
   (`platform: 'web'`, `token` = endpoint, ключи — `webPush`): глобально уникальна (endpoint переходит к вошедшему),
   ≤ 10 устройств на пользователя, привязана к сессии входа (после выхода, сброса пароля, отзыва push не уходят),
   снимается при удалении аккаунта. Миграции нет — индексы `push_tokens` подходят.
2. **Свой адаптер без новых зависимостей:** шифрование aes128gcm (RFC 8291) на `node:crypto`, VAPID (RFC 8292) —
   JWT ES256 через `jose`. Проверка — тест-вектор RFC 8291 Appendix A. Пакет `web-push` не берём: та же логика плюс
   транзитивные зависимости.
3. **SSRF.** Сервер шлёт POST на адрес от клиента, поэтому endpoint — только `https` на хостах push-сервисов
   (`fcm.googleapis.com`, `*.push.services.mozilla.com`, `*.notify.windows.com`, `*.push.apple.com`) — контракт и
   повторно адаптер; без редиректов, таймаут 10 с, тело ответа не читается.
4. **Ответы push-сервиса:** 201 — принято; 404/410 — подписки нет, документ снимается сразу; 429/5xx/сеть — если
   никто не принял, ретрай задачи; прочие 4xx — `failed` подписки.
5. **Payload** — `{ title, body, target }`: снимок текста и цель из белого списка, без адресов и ПДн; зашифрован
   ключом подписки. Service worker строит путь по цели своей копией белого списка (паритет с приложением — тест),
   нажатие фокусирует открытое окно и передаёт цель приложению или открывает новое.
6. **Флаги и ключи.** `WEB_PUSH_ENABLED` + `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` — независимо от
   `PUSH_ENABLED` (Expo); канал push выключен (`push_off`), только если выключены оба. Пара проверяется на старте.
   Приватный ключ — только env сервера; на dev пару создаёт `bootstrap.sh` на сервере. Публичный ключ клиент берёт из
   `GET /v1/notifications/web-push` (`null` — опции нет): ротация без пересборки web.
7. **Платформы:** опция есть, если в браузере есть Service Worker, Push API и Notification, а на iOS/iPadOS
   приложение запущено как установленная PWA (standalone). Разрешение — только по нажатию (N5).

## Последствия

- Смена пары VAPID делает старые подписки недействительными: push-сервис отвечает 403/410, приложение при
  следующем запуске видит другой ключ и переподписывается.
- `pushsubscriptionchange` в service worker не регистрирует новую подписку (у SW нет access token) — это делает
  приложение при следующем запуске.
- Квитанций у Web Push нет: «принято push-сервисом» = `sent`.

## Альтернативы

- Пакет `web-push` — работает, но лишние зависимости ради ~60 строк криптографии (отклонено).
- Отдельная коллекция подписок и свой pipeline — дублирует уникальность, лимиты, привязку к сессии и стирание
  (отклонено: «без параллельной системы»).
- Публичный ключ — build-arg web-сборки — ротация требует пересборки, нет способа выключить с сервера (отклонено).
