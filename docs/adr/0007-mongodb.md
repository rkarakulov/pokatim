## Контекст

Решение автора: проект целиком на MongoDB. База app-foundation с 0.4.0 поддерживает `database: mongo`
(`@rkarakulov/api-kit/mongo`, `@rkarakulov/test-kit/mongo`: клиент, транзакции, outbox, мигратор, стенд тестов).
Данные dev не переносятся, prod ещё нет. PostGIS в коде не использовался (только `CREATE EXTENSION`), геофункций
пока нет. Гарантии гонок слайсов 1–3 онбординга держались на `SELECT … FOR UPDATE` и перепроверке `WHERE`
после ожидания блокировки строки — в MongoDB такого ожидания нет (конфликт записи и повтор транзакции).

## Решение

- **MongoDB 8.0, single-node replica set** (транзакции и outbox работают только на RS; `MongoModule` проверяет RS на
  старте). Dev и CI — `mongo:8.0` без auth на `127.0.0.1`; dev-сервер — `mongo:8.0@sha256` с keyfile и
  пользователями: root — только администрирование, приложению — `pokatim` с `readWrite` на свою БД (Q1); пароли и
  keyfile генерирует сервер. Проект — рендер шаблона `v0.4.1` с `database: mongo` плюс домен.
- **Сериализация аккаунта (R1):** первая операция каждой транзакции, меняющей документы аккаунта, —
  `lockUser` = `users.findOneAndUpdate({ _id }, { $inc: { version: 1 } })`. Две транзакции одного аккаунта пишут один
  документ — вторая получает конфликт записи, `MongoTransactions.run` повторяет её колбэк на свежем снимке (аналог
  ожидания `FOR UPDATE` с перечитыванием). Вне транзакций — только атомарные операции над одним документом.
- **Ротация refresh (R3)** — один `findOneAndUpdate` с pipeline-обновлением: `previousRefreshTokenHash` берёт
  значение документа до обновления, значения — через `$literal`; параллельные ротации одного токена
  сериализуются на документе — проходят ровно две. Удалённость пользователя — чтение `users` до ротации; окно гонки
  закрывает инвариант «удаление аккаунта отзывает все сессии в той же транзакции».
- **Без CHECK и FK (R4, R5):** инварианты держат TS-интерфейсы, единственный писатель (репозиторий) и int-тесты;
  каскад удаления — явный, транзакция на аккаунт (очистка неподтверждённых). `$jsonSchema` не используем.
- **Индексы — только миграциями** (`0002_identity`, имена — из прежней схемы); **TTL-уборка** (Q2): сессии, ссылки и
  токены регистрации удаляются через 30 дней после `expiresAt` (`0003_identity_ttl`); истечение по-прежнему
  проверяет сервер.
- **Геоданные (R11, Q3):** GeoJSON + `2dsphere` в MongoDB для «рядом»/bbox по упрощённой геометрии; коридор,
  длина, прогресс по маршруту, правдоподобие — чистые функции `packages/tracks` в worker; сырые точки — S3.

## Альтернативы

- **Остаться на PostgreSQL + PostGIS** — против решения автора.
- **Сериализация через коллекцию блокировок с lease** — истечение, уборка, зависания при падении процесса.
- **Вложить сессии и ссылки в документ пользователя** — неограниченные массивы, горячий документ на каждый refresh.
- **`$jsonSchema`-валидаторы** — второй источник схемы рядом с TS-интерфейсами.
- **PostGIS отдельной БД для гео** — две БД на одну VPS.

## Последствия

- Каждая гарантия гонки проверяется int-тестом на реальном RS (ворота и удерживаемая транзакция,
  `pokatim-tests.md`), ключевые — с отрицательным доказательством.
- Нет в MongoDB: буфер линии, расстояние точка↔линия, длина и упрощение линии, линейная привязка, кластеризация,
  починка геометрий, проекции — это код `packages/tracks` (новая гео-библиотека — отдельным решением задачи треков).
- Конфликт транзакций одного аккаунта — повтор с backoff драйвера вместо очереди на блокировке; argon2 и побочные
  эффекты — вне колбэка транзакции (исключение — `takeResendAllowance` регистрации, R12).
- **Откат через границу БД через `image_tag` невозможен** (Q5): образы до перехода ждут PostgreSQL. Первый деплой
  после перехода удаляет контейнер и том `pgdata` стека после зелёного smoke; возврат — только compose-файлы и
  образы до перехода с пустой БД (runbook деплоя).
- Бэкап — ручной `mongodump` (runbook); ночной дамп в S3 — задача `backup-restore`.
- Пересмотреть: прод — replica set из 3 узлов или Atlas с TLS; гео-нагрузка, которой не хватит `2dsphere` и TS.
