# 0005. Вход по паролю и жизненный цикл refresh: окно повтора, reuse detection, лимиты входа

- Статус: Accepted
- Дата: 2026-10-24
- Пересмотр 2026-10-26: реализация на MongoDB — [ADR-0007](0007-mongodb.md) (`FOR UPDATE` → `$inc version` в транзакции,
  `UPDATE … RETURNING` → `findOneAndUpdate`); гарантии прежние

## Контекст

Слайс 2 онбординга (`docs/tasks/2026-10-24-onboarding-02-sign-in/task.md`): вход по e-mail и паролю на всех
платформах, выход, сессия на native. F5b ввёл строгую ротацию refresh без окна повтора: потерянный ответ refresh
(мобильная сеть, закрытая вкладка) выкидывал из аккаунта, а предъявление старого токена не отличалось от мусора —
кражу refresh нельзя было заметить. Прототип требует блокировку входа на 15 мин после нескольких неудачных попыток.
Ограничения: `RateLimiter` базы умеет только `consume` (нет `peek`/`reset`), свой лимитер в проекте запрещён
(AGENTS.md §2, §4.4); нейтральные ответы без оракула существования аккаунта (`pokatim-security.md`).

## Решение

1. **Вход** — `POST /v1/auth/session/sign-in` (под `SESSION_COOKIE.path`: вход видит прежнюю cookie браузера и
   отзывает её сессию — `superseded`). Ответ по `sessionTransport`, как у poll. Неверный пароль, неизвестный и
   удалённый e-mail — один и тот же `401 INVALID_CREDENTIALS`; для неизвестного адреса argon2 проверяет пароль
   по хешу-пустышке тех же параметров (время ответа не выдаёт аккаунт). Неподтверждённый аккаунт с верным паролем
   получает не сессию, а новый токен регистрации (`verificationRequired`, AD-28) — экран «Подтвердите e-mail».
2. **Лимиты входа** (Redis, `RateLimiter` базы, ключи — HMAC e-mail и IP): пара e-mail+IP — 5, e-mail со всех
   IP — 20, IP — 50 попыток за 15 мин; IPv6 — по сети /64. Счётчики проверяются по очереди (IP → e-mail+IP →
   e-mail) до первого отказа: попытки сверх лимита одного адреса не копят общий счётчик e-mail. Считаются все
   попытки в фиксированном окне (не только неудачные); отказ —
   `429 RATE_LIMITED` + `retryAfterSec` до проверки пароля, одинаково для существующих и несуществующих адресов.
3. **Ротация refresh** — один условный `UPDATE`: принимается текущий refresh или предыдущий в окне повтора 60 с
   (`previous_refresh_token_hash`, `rotated_at`). Предыдущим становится текущий хеш строки до обновления, поэтому
   брошенный при повторе токен тоже ловится. Предыдущий вне окна — **reuse detection**: сессия отзывается
   (`revoked_reason = 'reuse_detected'`, лог — только `sid`), ответ — тот же 401.
4. **Срок сессии скользящий:** 30 дней от каждой ротации, но не дальше 180 дней от входа.
5. **Выход** принимает текущий или предыдущий refresh (гонка выхода с ротацией не оставляет живую сессию);
   `revoked_reason = 'signed_out'`.
6. **Native:** сессия восстанавливается локально (офлайн-старт остаётся в аккаунте), затем фоновая ротация refresh
   по телу; 401 — локальный выход и экран «Вход»; сеть (одна немедленная повторная попытка), 429, 5xx — остаёмся.
   Сессионные операции приложения сериализованы замком в памяти процесса (вход и poll сохраняют сессию внутри
   той же операции); web — прежний Web Lock, вход — под ним. Web-выход без подтверждения сервера оставляет
   признак незавершённого выхода: запуск не восстанавливает аккаунт по cookie и повторяет отзыв.

## Альтернативы

- **Блокировка только по e-mail** (буква прототипа): любой, кто знает адрес, держит владельца вне аккаунта.
  Нет — пара e-mail+IP с общими потолками.
- **Примитив «N неудачных» в api-kit** (`check/registerFailure/reset`, блокировка ровно 15 мин после N-й ошибки):
  требует релиза app-foundation до слайса. Отложено (follow-up при переносе identity в базу); расхождение видно
  только при 5+ входах за 15 мин.
- **Таблица истории всех хешей refresh:** ловит любые старые токены, но растёт на каждую загрузку web-страницы, а
  старые токены и так мертвы. Нет.
- **Предыдущий токен действует до следующей ротации (без окна):** нет ложных выходов, но укравший получает рабочую
  сессию до следующего захода владельца (на native — дни). Нет.
- **Отзыв всех сессий пользователя при reuse:** «выйти везде» — вместе со сбросом пароля (слайс 3).
- **Блокирующий refresh при старте native** (как web): офлайн-старт показывал бы «Нет соединения» вместо вкладок.

## Последствия

- Потерянный ответ refresh переживается в пределах 60 с; повтор позже (приложение убито во время запроса) — reuse →
  вход по паролю. Цена — ввод пароля, данных не теряем.
- Браузеры без Web Locks при гонке вкладок могут оставить в cookie «предыдущий» токен → через 60 с выход.
- Параллельные refresh одним токеном: проходят ровно два (текущим и повтором в окне).
- Аудит входов — только `sessions.revoked_reason` + `revoked_at` и структурный лог; журнал входов (append-only) —
  отдельной задачей, если понадобится разбор инцидентов.
- Неподтверждённый вход перевыпускает токен регистрации: прежний на другом устройстве перестаёт действовать.
- Пересмотреть: при переносе identity в app-foundation (лимитер `peek/reset`), со сбросом пароля (отзыв всех
  сессий по `user_id`), с первым авторизованным эндпоинтом (авто-refresh по 401, `AppState`).

## Пересмотр (слайс 3, 2026-10-25)

Сброс пароля (ADR-0006), решение в силе. Дополнения:

- Смена пароля по ссылке отзывает **все** живые сессии пользователя одним `UPDATE` по `user_id`
  (`revoked_reason = 'password_reset'`); новых сессий сброс не выдаёт.
- Вход сверяет хеш пароля под замком аккаунта (`lockUserCredentials`): пароль проверяется до транзакции, и вход,
  проверивший старый пароль до коммита сброса, получает тот же `401 INVALID_CREDENTIALS` без сессии.
