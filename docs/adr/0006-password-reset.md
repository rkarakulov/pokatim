# 0006. Сброс пароля: токен ссылки, нейтральный запрос, отзыв всех сессий, без автоматического входа

- Статус: Accepted
- Дата: 2026-10-25
- Пересмотр 2026-10-26: реализация на MongoDB — [ADR-0007](0007-mongodb.md) (`FOR UPDATE` → `$inc version` в транзакции,
  `UPDATE … RETURNING` → `findOneAndUpdate`); гарантии прежние

## Контекст

Слайс 3 онбординга (`docs/tasks/2026-10-25-onboarding-03-password-reset/task.md`): райдер, забывший пароль, на любой
платформе запрашивает ссылку по e-mail и задаёт новый пароль. Правила безопасности (`pokatim-security.md`): ссылки
одноразовые, с TTL, открытие ничего не меняет, действие — POST; при сбросе инвалидируются все сессии; нейтральные
ответы без оракула существования аккаунта. Образцы — подтверждение e-mail (ADR-0002: токен = HMAC от id строки,
outbox → письмо, захват отправки) и вход (ADR-0005: лимиты `RateLimiter`, нейтральные ответы).

## Решение

1. **Ссылка** `${APP_LINK_BASE}auth/reset/<token>` — одна база окружения, как у подтверждения (R1). Токен —
   `base64url(HMAC-SHA256(EMAIL_TOKEN_SECRET, "password-reset:" + id))`, в БД — sha256 (`password_reset_tokens`);
   префикс назначения отличает его от токена подтверждения (общий вывод `deriveLinkToken`). TTL — 1 час (Q1);
   активна только последняя ссылка (Q6): новая заменяет прежние (`superseded_at`).
2. **Запрос** `POST /v1/auth/password-reset` — один и тот же ответ `{ resendAvailableInSec }` для любого адреса (R2).
   Лимиты — до БД, HMAC-ключи, по очереди до первого отказа: IP 20 в час (IPv6 — /64), затем e-mail — пауза 60 с и
   5 писем в сутки (Q5); 429 одинаков для существующих и несуществующих адресов. Письмо — только существующему не
   удалённому аккаунту, в том числе неподтверждённому (Q4); неизвестному адресу не шлём (Q11).
3. **Чтение** `GET /v1/auth/password-reset/:token` — без побочных эффектов: `valid` | `expired` | `used`;
   неизвестный токен и удалённый аккаунт — 404.
4. **Смена** `POST /v1/auth/password-reset/confirm` — ссылка проверяется до argon2, затем одна транзакция под
   `lockUser` с перепроверкой ссылки: новый хеш (argon2id), ссылка `used`, **все** живые сессии пользователя
   отозваны (`revoked_reason = 'password_reset'`), токен регистрации погашен, неподтверждённый e-mail подтверждён,
   outbox-событие письма «Пароль изменён». Устаревшая/использованная ссылка — `410 LINK_EXPIRED` (новых кодов нет,
   R8). Сессию сброс **не выдаёт** (Q2, R3): путь вне `/v1/auth/session`, cookie сессии не трогает; клиент
   показывает «Пароль изменён» → «Вход» с подставленным e-mail; сессия этого устройства — локальный выход (Q9).
5. **Вход сверяет хеш пароля под замком аккаунта** (R4): вход, проверивший старый пароль до коммита сброса,
   сессию не получает.
6. **Письма** — очередь `identity-email`, один процессор-диспетчер по `job.name` (R6): ссылка подтверждения и ссылка
   сброса (общий захват отправки), «Пароль изменён» (время по Минску, без ссылки с токеном; at-least-once).
7. **Web:** `Referrer-Policy: no-referrer` для путей `/auth/*` (R9) — токен из пути не уходит в `Referer`.

## Альтернативы

- **Сессия в ответе confirm** (R3б): на шаг короче, но путь под `SESSION_COOKIE.path`, Web Lock, и сессия появляется
  там, где открыли письмо (часто не то устройство). OWASP рекомендует не входить автоматически. Нет.
- **Все неистёкшие ссылки действуют до первого использования:** лучше при задержке писем, но «какое письмо
  открыть» перестаёт иметь ответ. Нет.
- **Тихо глотать запросы сверх паузы (всегда 200):** нет оракула, но интерфейс говорит «отправили», когда письма
  нет. Нет — 429 по HMAC адреса и так одинаков для любых адресов.
- **Идемпотентный 200 на повтор confirm:** соврёт, если повтор пришёл с другим паролем. Нет — 410 и повторный GET.
- **Проверять пароль входа под замком:** argon2 (~50 мс) держал бы строку `users`. Нет — сверка хеша под замком.
- **Отдельная очередь писем сброса:** без рефакторинга процессора, но ещё одна очередь на тот же SMTP. Нет.

## Последствия

- Выданный access JWT живёт ≤ 15 мин после сброса: авторизованных эндпоинтов пока нет; с первым AuthGuard —
  проверка `sid` или принятые 15 мин.
- Другие вкладки и устройства узнают об отзыве при следующем refresh/старте (без BroadcastChannel/`AppState`).
- Лимит e-mail запроса сброса (5 в сутки) общий для всех IP: посторонний, знающий адрес, может его выбрать, и
  владелец до суток ждёт письмо (429 с отсчётом). Follow-up — ключ e-mail+подсеть (как пара e-mail+IP у входа).
- Лимитер без `reset`: исчерпанные до сброса попытки входа ждут конца окна (≤ 15 мин).
- Аудит — `password_reset_tokens.created_at/used_at`, `sessions.revoked_reason`, структурный лог `{ uid, revoked }`;
  журнала `auth_events` нет (Q10).
- Неподтверждённый аккаунт, занятый чужой регистрацией, владелец забирает сбросом; дата рождения и согласия
  остаются от регистрации (продуктовый нюанс Q4).
- Очистка истёкших и использованных строк `password_reset_tokens` — задача обслуживания (позже).
- Пересмотреть: с первым авторизованным эндпоинтом (access после сброса, мгновенный выход вкладок), с universal
  links (слайс 5), при переносе identity в app-foundation.
