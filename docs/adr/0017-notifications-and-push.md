# 0017. Уведомления: модуль `notifications`, push через Expo, текст — снимок сервера

- Статус: Accepted
- Дата: 2026-10-27
- Задача: `docs/tasks/2026-10-27-notifications`
- Продукт: `docs/product/notifications.md` (N1–N12)

## Контекст

Райдер узнаёт о результатах, спорах и райдах, только открыв каждый экран. AGENTS §1 и §4.9 запрещали push в MVP,
`docs/product/account.md` A6 — тоже. Решение A11 эпика результатов: уведомления — отдельный модуль, источники только
пишут события. Outbox базы (`@rkarakulov/api-kit`) ведёт тип события в одну очередь.

## Решение

1. **Push — Expo Push Service** на iOS и Android (`expo-notifications`; токен — `getExpoPushTokenAsync` с EAS
   `projectId`). Новый внешний сервис: исходящий HTTPS только на `exp.host` (в production адрес из env другим быть не
   может). Web push — нет: в web уведомления видны в центре и на колокольчике. **Снято ADR-0022:** Web Push в PWA —
   второй транспорт того же канала.
   **Дополнено ADR-0023 п. 12:** четвёртая группа «Мероприятия» (напоминание `event_reminder`, push и письмо),
   цель `ticket`, тумблеры группы — подресурс `GET|PUT /v1/notifications/settings/events` (форма `/settings` прежняя).
   **Дополнено (notifications-fanout, 2026-10-30):** пятая группа «Маршруты» — решения по заявке своего маршрута
   (`route_published`, `route_rejected`), только push; подресурс `GET|PUT /v1/notifications/settings/routes`
   (`push.routes`, нет поля — значение `push.rides`). Группа хранится в документе уведомления: прежние `route_*` с
   `group: 'rides'` доставляются по тумблеру «Райдов».
   **Дополнено (achievements-push N1, 2026-10-31):** шестая группа «Достижения» — `achievement_granted` (новое
   достижение, уровень, сезонное), только push, по умолчанию включена без наследования; подресурс `GET|PUT
   /v1/notifications/settings/achievements` (`push.achievements`, нет поля — включено). Новый источник
   `achievements.grant-noticed` (15 типов в `notificationsOutboxRoutes`), порт `ACHIEVEMENT_NOTICES`
   (`AchievementsSyncModule`). Выдача, найденная сверкой при чтении (`origin: 'read'`, райдер в приложении), — в центр
   без push: `push.skipped`, `reason: 'in_app'` (`NoticeDraft.inApp`, `initialDelivery(…, { inApp })`); серверная
   сверка (`origin: 'server'`, PR N2) — по тумблеру группы. Схлопывание `achievement:<grantId>` по рангу (`seq`): одно
   уведомление на (выдача, уровень), новый уровень заменяет прежний.
2. **Модуль `notifications`** — единственный потребитель событий для уведомлений. Модули-источники (`results`,
   `disputes`, `rides`, `routes`) пишут только outbox в своих транзакциях (payload — id и коды, без `userId` и текстов) и дают
   порт чтения получателей и полей текста через `index.ts`. Чужих коллекций `notifications` не читает.
3. **Текст рендерит сервер при создании** и хранит снимком (словарь модуля, не `@pokatim/i18n`); цель перехода — тип
   и id из белого списка (`race`, `ride`, `dispute-response`, `my-route`; позже `ticket`, `profile-edit`,
   `achievement` — код из строгого `AchievementCode` и `seasonId?`), адресов нет. **Уточнение (achievements-push,
   RC-P5):** имена достижений, уровней и объектов («Подиум», «Серебро», «Гонка «…»») — строки каталога `@pokatim/i18n`
   (`achievements.*`, как карточка достижения `sharing`), второго каталога в модуле нет; снимок по-прежнему рендерит
   сервер. Незнакомая цель в ответе —
   `{ type: 'unknown' }`, приложение не переходит; из push — открывает центр.
4. **Доставка at-least-once.** Захват (lease) в документе уведомления, ретраи BullMQ, повтор задачи не шлёт второй
   push или письмо. Остаточный риск — дубль при падении worker между ответом Expo/SMTP и записью факта.
5. **Outbox «тип → одна очередь».** `results.protocol-published` и `results.result-revised` теперь уходят в
   `notifications-intake` (маршруты объявляет подписчик — `notificationsOutboxRoutes`). Слайсу 08 (рейтинг сезона) те
   же события нужны тоже — **fan-out — задача в app-foundation**: `OutboxRoutes = Record<string, string | readonly
   string[]>`, jobId = id события в каждой очереди. Альтернативы: intake уведомлений ставит задачу рейтинга (связывает
   несвязанные модули — нет); `results` пишет второе событие для 08 (дубль источника — только как временная мера).
   События, уже опубликованные в `notifications-intake`, слайсу 08 не достанутся — ему нужен бэкфилл по
   `race_recalculations`.
   **Отметка (race-results-08, DV-1):** слайс 08 обошёлся без событий — регламент `standings.sync` раз в минуту
   сверяет отпечаток источника сезона (гонки с протоколом и их текущие ревизии) и пересчитывает изменившиеся сезоны;
   бэкфилл не нужен. Fan-out и подписка рейтинга на события — follow-up.
   **Отметка (outbox-fanout, 2026-10-31):** fan-out outbox сделан в `@rkarakulov/api-kit` 0.6.0 (app-foundation PR #21):
   `OutboxRoutes` — очередь или массив очередей, задача в каждой очереди с jobId = id события, `mergeOutboxRoutes`
   объединяет маршруты подписчиков (pokatim — `src/outbox-routes.ts`). Регламенты `standings.sync`, `achievements` и
   сверка `route-rides` пока не заменены: подписка каждого на события — отдельная задача (бэкфилл уже опубликованных
   событий не нужен — регламент остаётся страховкой или убирается с ней).
   **Отметка (standings-outbox-events, 2026-10-31):** `standings` подписан на `results.protocol-published` и
   `results.result-revised` (`standingsOutboxRoutes` → `standings-recalc`); регламент `standings.sync` — страховка раз
   в 15 мин и при старте worker (бэкфилл не нужен).
   **Дополнение (notifications-fanout, 2026-10-30) — пачки получателей.** Не путать с fan-out outbox выше (тип → несколько
   очередей, api-kit 0.6.0): это раскладка **одного** события по получателям внутри `notifications`. Аудитория
   события (сумма уникальных получателей непустых черновиков) больше `NOTIFICATIONS_POLICY.fanoutChunk` (200) — intake
   сам не пишет, а ставит задачи-пачки `notifications.fanout` в ту же очередь `notifications-intake` (≤ 200 получателей,
   снимок текста, цели получателей пачки; порты источников в пачке не перечитываются). План раскладки сохраняется в
   данных задачи intake (`job.updateData`, поле `fanout`) **до** постановки; повтор intake с планом порты не зовёт
   (состав зафиксирован). Пачки ставит одна `FlowProducer.addBulk` плоскими узлами (`MULTI`; `Queue.addBulk` —
   pipeline), опции — явно `defaultJobOptions` очереди. `MULTI` не гарантирует успеха команд: `addBulk` молча
   пропускает ошибку отдельной команды (OOM Redis при `noeviction`) — после постановки каждый jobId плана проверяется в
   очереди, недостающие ставятся ещё раз, всё ещё нет — исключение, ретрай intake дотягивает их по плану. jobId пачки
   `fanout-<событие>-<черновик>-<пачка>`, повтор постановки дублей не создаёт. Пачка проверяет возраст события (72 ч),
   пишет прежним `writeNotices` и ставит доставку только по своим получателям; последняя попытка — лог
   `notifications.fanout_failed`. Повторная публикация события (новая задача intake без плана) раскладывает его заново —
   дублей уведомлений нет (уникальный `(sourceEventId, userId)`). Смешанные версии: старый worker на
   `notifications.fanout` бросает `unknown job` (ретраи, затем failed-набор — выкатывать worker целиком); откат сервера
   после записи `push.routes` — поле не читается, решения по маршруту снова идут по тумблеру «Райдов».
6. **Поправка ADR-0013 п. 2.** «Я иду», правка и отмена райда — по-прежнему одна условная операция над документом
   (фильтр с лимитом, статусом, временем, членством), но в транзакции с outbox. Замков и чтения-проверки нет.
7. **Хранение.** Уведомления — 90 дней (TTL), квитанции Expo — 24 ч. Push-токены — до снятия: выход (запрос до отзыва
   сессии), `DeviceNotRegistered` в тикете или квитанции, удаление аккаунта (все токены — в транзакции удаления, шаг
   стирания `notifications` убирает уведомления, настройки, токены и тикеты). Токен привязан к сессии регистрации
   (`sessionId` из `AuthGuard`): push уходит только на токены живых сессий (порт `IdentityAccounts.liveSessionIds`),
   токены отозванных выходом, сбросом пароля, reuse detection или истёкших сессий снимаются при доставке.
8. **Тихие часы** — настройка райдера, целые часы по Минску, по умолчанию 22–8; push откладывается до конца интервала,
   несколько отложенных — одна сводка; в центре уведомление появляется сразу; письма тихие часы не задерживают. Лимит —
   20 push в час на райдера, сверх — только центр.
9. **Секреты и флаги.** `EXPO_ACCESS_TOKEN` — только env (необязательный); `PUSH_ENABLED=false` по умолчанию — без
   него push помечается `skipped`, центр работает. Разрешение push приложение спрашивает только по нажатию (N5).

## Последствия

- Выкат без EAS `projectId` и ключей APNs/FCM: центр и колокольчик работают, push не регистрируется
  (`docs/runbooks/push.md`).
- Накопленные до выката события протоколов и споров публикуются в intake и отсекаются по возрасту (> 72 ч).
- Параллельные «Я иду» на один райд конфликтуют в транзакции и повторяются драйвером вместо сериализации на документе;
  для ≤ 100 участников приемлемо.
- Видимость провала доставки — лог `notifications.push_failed` и failed-набор BullMQ; экран в панели — follow-up.

## Альтернативы

- Нативные APNs/FCM напрямую — два протокола и ключа на сервере вместо одного Expo (отклонено).
- WebSocket / реальное время — вне рамок MVP; счётчик — polling 60 с (отклонено).
- Текст на клиенте по коду события — старые сборки не знают новых событий, локализация двух мест (отклонено).
