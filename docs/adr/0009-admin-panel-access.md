# 0009. Доступ к панели «Протокол»: роль на аккаунте приложения, отдельная серверная сессия панели

- Статус: Accepted
- Дата: 2026-10-25
- Задача: `docs/tasks/2026-10-25-admin-01-foundation` (R1–R3, R7, R8, C1, C3)

## Контекст

Команде платформы (администратор, модератор, организатор) нужна веб-панель «Протокол» (`apps/admin`). Автор решил
(D-13, 2026-10-25): один аккаунт на человека — вход в панель тем же e-mail и паролем, что в приложении, роль команды
выдаётся существующему пользователю приложения; прод — `/admin/` того же домена (Q13). Прежняя модель «отдельные
служебные аккаунты» (дизайн F6 §7) для pokatim отменена. Нужно: изолировать панель от кражи сессии приложения
(refresh в SecureStore телефона, cookie web, access в памяти — срок до 180 дней), мгновенно гасить доступ при смене
пароля, снятии роли и удалении аккаунта, проверять права на сервере и вести append-only журнал.

## Решение

1. **Роль — данные контекста `panel`**, не поле `users`: коллекция `panel_members` (`_id` = id пользователя, роль,
   статус, имя в панели), единственный писатель — `PanelRepository`. Identity о панели не знает.
2. **Отдельная серверная сессия панели**, не JWT: непрозрачный токен в cookie `__Secure-pokatim_admin_sid`
   (`HttpOnly; Secure; SameSite=Strict; Path=/v1/admin`, без `Domain`), в БД — sha256; простой 2 ч, абсолют 12 ч.
   Вход — только паролем через узкий порт identity `PanelCredentials` (та же проверка, что вход приложения:
   `CredentialsCheck`). Access JWT и refresh приложения панель не принимает.
3. **`PanelGuard` на каждом запросе:** сессия жива → аккаунт приложения не удалён и подтверждён → **штамп учётных
   данных** (`HMAC(EMAIL_TOKEN_SECRET, "credentials:" + passwordHash)`, считает identity) совпадает с записанным при
   входе → член команды `active` → права роли (`ROLE_PERMISSIONS`, только сервер). Смена пароля гасит сессии панели без
   записи из identity в `panel` и закрывает гонку «вход ↔ сброс»; снятие роли отзывает сессии в своей транзакции.
4. **Общие счётчики входа** (`signin-*`) с приложением: один пароль — одна цель перебора.
5. **«Последний администратор»** — транзакции, меняющие набор активных админов, первой операцией пишут документ-замок
   `panel_meta.admins` (`$inc version`): write skew «два админа снимают друг друга» невозможен.
6. **Журнал** `panel_audit` — append-only (`PanelAudit.append(tx, …)` в транзакции действия; без e-mail, IP, UA):
   выдача, смена, снятие роли (в том числе CLI `grant-admin`), вход и выход. Будущие модули панели пишут в него
   через `modules/panel/index.ts`.
7. **Первый и аварийный администратор** — CLI `node dist/cli/panel.js grant-admin --email … --name …` на сервере.

## Альтернативы

- **Access JWT приложения + `AuthGuard` + проверка роли:** переиспользование, но украденный access/refresh
  приложения (в том числе с телефона) открывает панель на срок сессии приложения. Нет.
- **«Step-up»: сессия приложения + повторный пароль раз в N часов:** та же поверхность, плюс сложность. Нет.
- **Событие outbox `identity.password-changed` → отзыв сессий панели:** окно в секунды и событийная связь ради одной
  проверки; поле `credentialsVersion` в `users` — правка всех путей смены пароля. Выбран штамп.
- **Отдельные счётчики лимитов панели:** удвоили бы число попыток на один пароль.
- **Отдельный хост панели:** сильнее изоляция от XSS web приложения; автор выбрал тот же домен (Q13) — пересмотр ниже.

## Последствия

- **Пароль приложения = доступ к панели (C1).** Отдельная сессия защищает от кражи сессии, но не пароля (фишинг,
  повтор паролей, сброс по почте сотрудника). Компенсации: общие лимиты, короткая сессия, штамп, журнал входов.
  **До прода обязательна 2FA (TOTP) для `admin`** (для `moderator` — рекомендуется) — отдельный слайс; до неё внешние
  организаторы в панель не допускаются.
- **Тот же домен `/admin/` (C3, принятый риск):** XSS в web приложения может слать same-origin запросы к
  `/v1/admin/*` от имени открытой в том же браузере сессии панели (Fetch Metadata покажет `same-origin`).
  Компенсации: строгий CSP панели (nginx образа `admin`), cookie с путём `/v1/admin` и `SameSite=Strict`, повторный
  пароль, короткая сессия, журнал; **до прода — строгий CSP web приложения** (SSR с nonce/хешами); рекомендация —
  панель в отдельном профиле браузера. Пересмотр — отдельный хост панели, если появится пользовательский
  HTML/Markdown в web приложения или 2FA не успеет к проду.
- Неудачные входы и «Нет доступа к панели» в журнал не пишутся (не член команды, шум).
- Перебор через панель блокирует и вход приложения этого адреса на ≤ 15 мин (и наоборот) — принято.
- Append-only держат код и тест-сторож; роль MongoDB без `update`/`remove` для `panel_audit` — follow-up.
- Удаление аккаунта (будущая задача) обязано снять роль и отозвать сессии панели; гард уже отказывает удалённому.
- Компоненты `apps/admin/src/ui` — кандидаты в `@rkarakulov/admin-kit` (F6, после слайса 2 панели).
