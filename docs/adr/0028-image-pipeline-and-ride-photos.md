# 0028. Конвейер изображений `media` и фото организатора кофе-райда

- Статус: Accepted
- Дата: 2026-10-31
- Задача: `docs/tasks/2026-10-31-ride-photo` (PR A — API, contracts, рендер 4a)

## Контекст

Организатор кофе-райда добавляет к своему райду фото: оно лежит под затемнением на герое ленты и Главной и на
карточке-приглашении 4a (`docs/product/rides.md`, ADR-0018 «`night` — 4a без фото»). Фото — UGC и ПДн (EXIF с GPS,
битые и огромные файлы). Механизм приёма уже есть у аватара (ADR-0019): sharp в HTTP-обработчике с жёсткими пределами,
один семафор обработки на процесс — бюджет памяти контейнера API (512 МБ) считан под **одну** обработку.

## Решение

1. **Общий конвейер изображений, хранение — у владельца (вариант C).** `apps/api/src/modules/media/` — инфраструктурный
   Nest-модуль-лист: без коллекций и без импортов `modules/*` (правило dependency-cruiser `media-leaf`). В нём:
   `detectImageFormat` (сигнатура), `inspectImage` (формат декодера = сигнатуре, предел пикселей по формату — JPEG/WebP
   100 Мп, PNG 25 Мп, размеры после EXIF-поворота), `decodeOriented` (стадия декода аватара), `processCover` (одна
   стадия: поворот + вписать в 1600 px без увеличения → JPEG q82), `replyJpeg` (заголовки отдачи), `MEDIA_POLICY`.
   Настройки sharp процесса (`cache(false)`, `concurrency(1)`, `failOn: 'error'`, `animated: false`,
   `sequentialRead`, таймаут 10 с) — **только** в `media/image-pipeline.ts`.
2. **Один гейт обработки и общие слоты приёма.** `ImageProcessing` (1 обработка на процесс на **все** фото, ожидание
   ≤ 5 с, иначе `429 retryAfterSec: 5`) и `ImageUploadSlots` (4 на процесс, 1 на пользователя) — провайдеры только
   `MediaModule` (не `@Global`); его импортируют `ProfileModule` и `RidesModule` — Nest создаёт статический модуль один
   раз, оба получают один экземпляр. Аватар и фото райда одного пользователя параллельно — `429` (R2). Бюджет ADR-0019
   сохраняется. В worker `MediaModule` не импортируется: рендеру карточек хватает чистых функций.
3. **Аватар — поверх ядра, без изменения поведения.** `processAvatar`/`cropRect`/`scaleRect` остаются в
   `profile/avatar-image.ts`, `detectImageFormat` реэкспортируется; коды `AVATAR_*`, заголовки и кэш на год — прежние.
4. **Фото райда — модуль `rides`.** Коллекция `ride_photos` (миграция `0047_ride_photos`, единственный писатель —
   `RidePhotosRepository`): `{ _id: randomToken, rideId (unique), organizerUserId, bytes, contentType, width, height,
   bytesLength, createdAt }`; ссылка — `rides.photoId` (без бэкфилла, `version` не меняется). Одно фото на райд;
   замена — новый id. Хранится только перекодированный JPEG без метаданных (исходник не хранится).
   - `PUT /v1/rides/:id/photo` — `AuthGuard`; до тела: свой райд (иначе 404) → будущий опубликованный (иначе 409
     `RIDE_INVALID_STATE`) → слот → лимит `ride-photo:<uid>` 20/ч; затем `readLimited` 10 МиБ (тишина 10 с, всё 60 с) →
     гейт → `processCover` (короткая сторона **результата** < 400 px — `422`, R4) → транзакция «условная запись райда
     первой → прежнее фото удалено → новое вставлено».
   - `POST /v1/rides/:id/photo/delete` — любой статус, идемпотентно, лимит `rides-manage`.
   - `GET /v1/ride-photos/:id` — `PublicReadGuard`; только текущее фото **нескрытого** райда (иначе 404 всем, включая
     организатора); `public, max-age=86400, immutable` (R6: снятое уходит из кэшей за сутки), `nosniff`,
     `CSP: default-src 'none'; sandbox`.
   - View (`RideCard`/`RideDetail`/`RideView`): `photo: { id } | null`; скрытый — `null` всем.
   - Модерация: `POST /v1/admin/rides/:id/photo-reset` (`rides.moderate`, `{ photoId, reason }`) — условная запись
     по `photoId` карточки первой → документ удалён → журнал `ride.photo_reset` (`details: null`, без id фото); фото
     уже другое — 409 `CONFLICT`; фото нет — 200 без журнала. Жалобы и `version` не трогаются (R10). Дополнение
     (ride-photo-followups): сброс пишет в той же транзакции outbox `rides.photo-reset { rideId, seq }` (`seq` —
     `noticeSeq` после записи) → уведомление организатору `ride_photo_reset` (группа «Райды», схлопывание по райду).
   - Просмотр модерацией (ride-photo-followups, R11 b): `GET /v1/admin/rides/:id/photo?photoId=` — `PanelGuard` +
     `rides.moderate`; текущее фото райда **любого** статуса (и скрытого) по паре `(rideId, photoId)`, не текущее —
     404; `private, no-store`, заголовки `replyJpeg`; просмотр не журналируется.
   - Стирание (ADR-0015, шаг `rides`): ссылки на всех райдах организатора → `null`, все его `ride_photos` удалены.
5. **Коды ошибок для новых потребителей — общие `IMAGE_*`** (R9): `IMAGE_FORMAT_UNSUPPORTED` (415), `IMAGE_TOO_LARGE`
   (413), `IMAGE_INVALID` (422, `details.reason: 'too_small' | 'unreadable'`, `tolerantEnum`). Аватар — на `AVATAR_*`
   навсегда (установленные клиенты).
6. **Рендер 4a с фото — worker `sharing`.** `RideInviteFacts.photoId` (OG — с ride-photo-followups, ниже), в ключе приглашения — только
   у `night`, `STORY_CARD_POLICY.renderVersion` 4. Байты — порт `RIDES_FOR_SHARING.invitePhoto(rideId, photoId)` (только
   текущее фото нескрытого райда, иначе `null` → задача `skipped`). Композиция в sharp: фото `cover` 1080×1920 → слой
   скрима (токен `photoScrim` из `@pokatim/design-tokens`, цвет `overlay.scrim`) → текстовый слой (тот же `nightCard`,
   прозрачный фон, текст — роль `onPhoto`) → `png({ palette: true, quality: 80, effort: 7, dither: 1 })`; не влез в
   `maxPngBytes` (2 МБ, прежний, R5; шумная фикстура ≈ 1,73 МБ) — одна попытка палитрой 16 цветов (4 бита), затем ошибка. Байты фото не идут через SVG/base64.
7. **Дополнение (ride-photo-followups, `docs/tasks/2026-11-01-ride-photo-followups/task.md`).**
   - Композиция «фото → скрим → текст → палитра» — общая `sharing/photo-card.png.ts` (`composeWithPhoto`,
     `encodePhotoCard`, `PHOTO_CARD_PALETTES`, `onPhotoColors`) для 4a и OG.
   - OG райда с фото: `photoId` в хэше OG, `OG_CARD_POLICY.renderVersion` 4; тот же макет, цвета `onPhoto` схемы вида,
     скрим `overlay.scrim` с профилем `photoScrimHero`; PNG с палитрой ≤ `OG_CARD_POLICY.maxPhotoPngBytes` (600 КБ;
     шумная фикстура влезает только палитрой 16 цветов ≈ 0,3 МБ). Байты — тот же `invitePhoto` (снято — `skipped`).
   - Картинка приглашения отзывается при отдаче: `story-card:ride:<token>` = `{ rideId, photoId нарисованного }` (той же
     `MULTI`, что PNG, тот же TTL) → `StoryCardImageService` сверяет порт `RIDES_FOR_SHARING.inviteCardLive` (райд не
     скрыт и фото текущее — `RidesRepository.isShareable`); нет — PNG и привязка удаляются, 404. Без событий и без
     ребра `rides → sharing`; гонка «рендер ↔ сброс» закрыта (PNG несёт старый `photoId`).

## Альтернативы

- **(A) Общий модуль `media` с коллекцией `media_images` (`ownerKind/ownerId`).** Права, видимость (скрытый райд),
  модерация и стирание доменные: общий модуль либо знает о райдах и профилях (цикл), либо требует портов на каждое
  правило; «на вырост» (`AGENTS.md` §4.9). Отклонено.
- **(B) Копия механизма аватара в `rides`.** Второй sharp-конвейер и второй семафор — пик памяти удваивается против
  бюджета ADR-0019; ~250 строк дублированной тонкой безопасности. Отклонено.
- **`src/media/` рядом с `upload-slots.ts`.** Граница через `index.ts` проверяется `arch:check` только внутри
  `modules/`, путь вне `paths:` правил безопасности (R1). Отклонено.
- **Свои слоты фото райда (2 + 2 или 4 + 4).** Удваивают буфер тел против ADR-0019 или режут аватар (R2). Отклонено.
- **JPEG для карточки 4a с фото / отдельный предел 4 МБ.** Смена контракта и имени файла (`<token>.png`) или рост Redis
  (R5). Отклонено.
- **`immutable` на год, как у аватара.** Фото райда снимают модерация, скрытие и стирание — год в кэше браузера (R6).

## Последствия

- Второе исключение из «файлы пользователей наружу не выдаются» (ADR-0011) после аватара: только перекодированный JPEG,
  только текущее фото нескрытого райда, доступ — по случайному id.
- Следующие виды фото (обложки гонок, галерея) берут `media` и коды `IMAGE_*`; OG райда с фото, шапка детали райда
  и фото скрытого райда в панели сделаны (ride-photo-followups); хранение и права — в модуле-владельце. Новый вид
  фото — проверить бюджет памяти: гейт по-прежнему один на процесс.
- Кандидат в app-foundation — только если второй проект попросит: конвейер привязан к sharp, политике памяти и
  контрактам pokatim.
- Принятые риски: кэш браузеров держит снятое фото до 24 ч; PNG приглашения (`private, max-age=86400, immutable`), уже
  скачанный устройством, держится в его кэше до суток, а сохранённые/отправленные файлы не отзываются (R2
  ride-photo-followups); токены приглашений, выданные до выката привязок, — без проверки до 24 ч; публичный HTTP-кэш OG
  (`public, max-age=86400`) и кэши превью соцсетей не отзываются; фото прошедших и отменённых райдов хранятся до удаления
  организатором или стирания аккаунта (≤ 1 на райд, ≈ 0,2–0,5 МБ; очистка по сроку — follow-up, R12); смена
  `renderVersion` перерисовывает все карточки сторис по запросу (кэш 24 ч).
- S3/CDN (ADR-0019): при переезде меняются репозитории и отдача, не конвейер.
