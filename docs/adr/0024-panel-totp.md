# 0024. 2FA (TOTP) для панели «Протокол»

- Статус: Accepted
- Дата: 2026-10-29
- Задача: `docs/tasks/2026-10-29-panel-2fa`
- Связано: ADR-0009 («Последствия», C1 и C3)

## Контекст

Вход в панель — тот же пароль, что в приложении (ADR-0009, C1), и панель живёт на том же домене (C3). Отдельная
сессия защищает от кражи сессии, но не от кражи пароля. До прода нужен второй фактор для `admin`, остальным ролям он
рекомендуется. Флаг обязательности не должен запирать dev-стенд и администраторов, которые 2FA ещё не подключили.

## Решение

1. **TOTP (RFC 6238) своими силами на `node:crypto`:** SHA-1, шаг 30 с, 6 цифр, окно ±1 шаг, base32 — свой; секрет
   20 байт. Повтор закрыт `lastUsedStep`: код принимается условным обновлением, только если его шаг больше записанного.
   Сравнение — `timingSafeEqual`.
2. **Секрет — шифротекстом:** AES-256-GCM, ключ `PANEL_TOTP_KEY` (hex 64, только env, на сервере генерирует
   `bootstrap.sh`; для шифрования и HMAC кодов — два подключа HKDF-SHA256, info `panel-totp-enc` /
   `panel-recovery-hmac`), формат `v1:<iv>:<tag>:<ct>`, AAD = `panel-totp:<userId>`. Без ключа подключение и вход сотрудника
   с 2FA отвечают `503 TOTP_UNAVAILABLE` (fail closed), нечитаемый секрет (сменённый ключ, порча) — тоже 503 и лог
   `secret_unreadable`; `PANEL_TOTP_ENFORCED=true` без ключа — отказ запуска.
3. **Коды восстановления:** 10 кодов `xxxxx-xxxxx` (base32, 50 бит), показываются один раз; в БД — HMAC-SHA256
   подключом HMAC. Принятие шага и гашение кода — условием и по эпохе прочитанного документа 2FA (подключена заново —
   отказ). Вход кодом восстановления гасит код условным `$set usedAt`. Перевыпуск — с текущим кодом TOTP.
4. **Второй шаг входа — вызов (challenge):** после пароля и проверки члена команды сервер выдаёт непрозрачный токен в
   теле ответа (`totpRequired` / `totpSetupRequired`). В БД — sha256, штамп учётных данных, назначение, срок 5 минут,
   не больше 5 попыток кода (каждая резервируется атомарно до проверки); погашение — только живого вызова. Сессия без
   второго фактора выдаётся под замком сотрудника (`lockMember`), который берёт и подтверждение подключения 2FA: под
   замком 2FA перечитывается, уже активна — вызов кода. Активация 2FA (вход и настройки) сверяет штамп учётных данных
   под замком аккаунта (порт identity `lockAccountState`): сброс пароля между проверкой и активацией — отказ. Успех гасит вызов в одной транзакции с созданием сессии; смена пароля между шагами
   (другой штамп) — `401 TOTP_CHALLENGE_EXPIRED`. Пароль повторно не пересылается.
5. **Обязательность — только `admin` при `PANEL_TOTP_ENFORCED=true`** (по умолчанию `false`). Admin без 2FA после
   верного пароля подключает её прямо на экране входа; сессия — только после подтверждения кода. Отключить себе 2FA
   при обязательности admin не может (`409 TOTP_REQUIRED`).
6. **«Запомнить устройство» на 30 дней:** cookie `__Secure-pokatim_admin_device` (`HttpOnly; Secure;
   SameSite=Strict; Path=/v1/admin/session`, без `Domain`), в БД — sha256, штамп учётных данных и эпоха 2FA. Пропускает
   только шаг кода. Гаснет при смене пароля, при любой смене 2FA (новая эпоха, отключение, сброс), по сроку; не больше
   10 устройств на сотрудника. Вход по устройству перепроверяет его в транзакции сессии условной записью документа
   устройства — конфликт записи упорядочивает вход со сбросом и отключением 2FA.
7. **Лимиты кода** (по образцу `CredentialsCheck`): `panel-totp-ip` 50 / 15 мин → `panel-totp-user` 10 / 15 мин (ключи —
   HMAC), списывается каждая попытка ввода кода (вход, подключение, перевыпуск, отключение).
8. **Сброс:** администратор сбрасывает 2FA другому сотруднику (`members.manage`, причина обязательна, себе — нельзя).
   Аварийный путь — CLI `reset-totp --email` с актором `cli`. Сброс в одной транзакции удаляет 2FA и доверенные
   устройства цели и отзывает её сессии панели (`totp_reset`). Отключение самим сотрудником его сессии не гасит.
9. **Журнал:** `panel.totp_enabled`, `panel.totp_disabled`, `panel.totp_reset`, `panel.totp_recovery_regenerated`,
   `panel.totp_recovery_used` — в транзакции действия. Неудачные коды в журнал не пишутся, только лог `uid` + причина.
10. Всё — модуль `panel` (2FA — свойство сотрудника панели, identity не меняется); коллекции `panel_totp`,
    `panel_sign_in_challenges`, `panel_trusted_devices` (миграция `0040_panel_totp`), `panel_sessions.secondFactor`.

## Альтернативы

- **Библиотека `otplib`/`speakeasy` в API:** лишняя зависимость ради ~60 строк, проверяемых векторами RFC. Нет.
- **argon2 для кодов восстановления:** 50 бит энтропии + лимиты делают перебор нереальным; быстрый HMAC с ключом из
  env достаточен и не открывает DoS через тяжёлый хеш. Нет.
- **Пароль повторно на втором шаге вместо вызова:** пароль ходит по сети дважды, второй шаг тратит счётчики `signin-*`.
  Нет.
- **WebAuthn / passkeys:** сильнее TOTP, но сложнее (регистрация ключей, восстановление, поддержка браузеров). Позже —
  отдельным решением.
- **Обязательность для всех ролей:** внешние организаторы — барьер входа; решение автора — только `admin`.

## Последствия

- Утечка БД не даёт секретов TOTP и кодов восстановления без `PANEL_TOTP_KEY`. Смена ключа делает все подключённые
  2FA нерабочими: сотрудникам — сброс (CLI) и повторное подключение.
- Включение обязательности (`PANEL_TOTP_ENFORCED=true`) технически без подготовки: admin без 2FA подключит её при
  следующем входе. Уже открытые сессии admin без второго фактора живут до своего срока (≤ 12 ч).
- Остаточный риск D2: при `PANEL_TOTP_ENFORCED=true` тот, кто знает только пароль admin без 2FA, первым подключит свой
  аутентификатор на экране входа. Порядок включения: admin подключают 2FA сами через «Безопасность», флаг включается
  после сверки колонки «2FA» в «Сотрудниках» (у всех admin — подключена).
- C1 закрыт для сотрудников с 2FA; C3 (тот же домен) остаётся принятым риском ADR-0009, строгий CSP web приложения —
  по-прежнему до прода.
- Удаление аккаунта бывшего сотрудника документ 2FA сейчас не стирает (шифротекст без ключа бесполезен) — follow-up
  вместе с уборкой `panel_*` при стирании.
