# 0015. Удаление аккаунта: оркестратор `account`, порты стирания модулей, маркер стёртого e-mail, повторный проход

- Статус: Accepted
- Дата: 2026-10-27
- Задача: `docs/tasks/2026-10-27-account-deletion`
- Продукт: `docs/product/account.md` (A1–A12)

## Контекст

App Store требует удаление аккаунта из приложения, Google Play — ещё и адрес удаления в вебе. Данные пользователя
лежат в коллекциях шести модулей (`identity`, `profile`, `rides`, `routes`, `tracks`, `devices`); каждую пишет только
её модуль (`pokatim-db.md`). Удаление сразу (A1): сессии отзываются мгновенно, данные — чистятся в фоне за минуты.
Журналы append-only хранятся (A9). Адрес удалённого аккаунта повторно не регистрируется (D-07, A4), но открытый e-mail
храниться не должен.

## Решение

1. **Оркестратор — модуль `account` без своих коллекций.** HTTP `POST /v1/account/delete` → лимит → роль панели (A11,
   порт `PanelMembership`) → пароль (`AccountClosure.verifyPassword` = `CredentialsCheck`, общие счётчики входа) → одна
   транзакция: `AccountClosure.close` (первой — `lockUserCredentials`, сверка хеша, `deletedAt`, отзыв всех сессий
   `account_deleted`, гашение ссылок и токена регистрации) + `PanelAudit` `account.deleted` + outbox
   `account.deletion-requested { userId }`. Ошибки: `403 PASSWORD_INCORRECT` (не 401 — клиент не уходит в refresh),
   `409 ACCOUNT_PANEL_MEMBER`, `429 RATE_LIMITED`.
2. **Один обработчик, а не fan-out событий.** Публикатор outbox базы отправляет тип в одну очередь; fan-out требовал бы
   N типов и терял бы порядок. Очередь `account-deletion`, процессор `AccountErasureProcessor` вызывает порты стирания
   модулей-владельцев по порядку: профиль → райды (подпись пропадает первой) → «Мои маршруты» → устройства (до треков:
   после отзыва новых приёмов нет) → заезды (+ маркеры источника и замок активностей) → identity (письмо «Аккаунт
   удалён», затем стирание ПДн). Каждый шаг идемпотентен; ретрай задачи повторяет все шаги. Живой аккаунт
   (`deletedAt = null`) не чистится.
3. **Порты стирания** — классы-провайдеры в «ядрах» модулей (`ProfileCoreModule`, `RidesCoreModule`,
   `RoutesCoreModule`, `TracksCoreModule`, `DevicesCoreModule`, `IdentityErasureModule`), экспорт через `index.ts`;
   каждый пишет только коллекции своего модуля и переиспользует его существующую логику удаления (`deleteOwn`,
   `TrackUploadsService.remove`, общий отзыв подключения `DeviceRevocation`). Граф: `account → identity, panel,
   profile, rides, routes, tracks, devices`; `account` не импортирует никто.
4. **Маркер стёртого e-mail в самом поле `email`**: `erased:<HMAC-SHA256(EMAIL_TOKEN_SECRET, 'deleted-email:' +
   email)>` одной атомарной записью вместе с `birthDate: null`, `passwordHash: null`, `erasedAt`. Полный
   `users_email_unique` не меняется; регистрация ищет адрес и его маркер (`409 EMAIL_UNAVAILABLE`); вход и сброс
   пароля по адресу маркер не находят (как неизвестный адрес). Новой переменной окружения нет. Письмо уходит до
   стирания (захват `deletionEmailClaimedAt` → `deletionEmailSentAt`); не ушло за 24 ч — стирание без письма (F8).
5. **Повторный проход.** Запрос, прошедший `AuthGuard` до удаления, может записать данные после очистки (R5). Первый
   проход ставит `account.deletion-sweep` через 15 мин (дедупликация `account-sweep:<userId>`); регламент
   `account.erasure-resume` раз в час ставит повторный проход удалённым раньше часа без `erasureSweptAt` (частичный
   индекс `users_erasure_pending_idx`, миграция 0023) — он же перезапускает финально упавшую очистку.

## Правило для будущих модулей

Шаг `profile` с rider-profile (ADR-0019) стирает и аватары (`profile_avatars` по `userId`) до документа профиля;
с profile-moderation — первыми жалобы **на** пользователя (`profile_reports` по `targetUserId`); поданные им жалобы на
других остаются с псевдонимным id.

Новый модуль с данными пользователя **обязан** дать порт стирания (идемпотентный, только свои коллекции, append-only
журналы не трогает) и шаг в `AccountErasureService` в нужном месте порядка, с int-тестом «данные удалены, чужие целы,
повтор безопасен».

## Последствия

- `account` зависит от всех модулей с данными пользователя — это осознанная цена порядка шагов.
- Ротация `EMAIL_TOKEN_SECRET` снимает блок D-07 со стёртых адресов (runbook).
- At-least-once письма: падение worker между отправкой и отметкой даёт второе письмо (как у ссылок).
- Пользователь Open Wearables (`pokatim:<id>`) остаётся до ручного удаления (A8, runbook).
- Видимость финального провала — лог `account.erasure_failed`, failed-набор BullMQ и регламент; экран в панели —
  follow-up.

## Альтернативы

- Fan-out событий по очередям модулей — нет порядка шагов, N типов событий (отклонено).
- Отдельное поле `emailHash` + частичный уникальный индекс — сужение индекса, expand/contract (отклонено).
- Коллекция заблокированных хешей — второй источник правды, write skew с регистрацией (отклонено).

## Дополнение: фото организатора райда (`docs/tasks/2026-10-31-ride-photo`, ADR-0028)

- Шаг `rides` (`RideErasure.erase`) после подписи организатора снимает `photoId` со всех его райдов (любой статус,
  включая скрытые и прошедшие) и удаляет все его документы `ride_photos` (индекс `ride_photos_organizer_idx`); лог шага —
  `… photos=N`. Порядок шагов не меняется, повтор — no-op.
